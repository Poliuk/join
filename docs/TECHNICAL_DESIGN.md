# Technical Design — Join!

*Status: approved 2026-10-05, updated to match the implementation after the redesign, for in-app updates, for 1.2.0 (2026-10-07, Settings regroup 2026-10-08, dismissing events 2026-10-15) and for 1.3.0 (repeating events, Install and Relaunch, Settings in front 2026-10-15; notifications 2026-10-16; Settings polish 2026-10-19) · Companion to PRODUCT_BRIEF.md*

## 1. Platform and stack

**Decision: native macOS app in Swift, SwiftUI for views, AppKit where SwiftUI falls short (the status item, the menu bar panel window, the alert windows and the Settings window). No third-party runtime dependencies.**

| Requirement | Why native wins |
|---|---|
| Read calendars | EventKit is an Apple framework; only reachable from native code. |
| Full-screen overlay above everything, on every display, over other apps' full-screen Spaces | Needs `NSWindow` level and collection-behavior control. Electron exposes some of this but not reliably across Spaces. |
| Menu bar app with no Dock icon | `LSUIElement` + `NSStatusItem`; first-class in AppKit. |
| Tiny footprint, always running | A native agent app idles at ~20–30 MB. An Electron shell idles at 150 MB+ for a menu bar app. |

Considered and rejected:

- **Electron** (author's home turf via Studio): worst fit for a persistent menu bar utility; EventKit would need a native addon anyway.
- **Tauri**: lighter than Electron but the calendar and overlay pieces still end up as Swift plugins; you'd write the hard parts in Swift regardless.

Targets: **macOS 14+**, the **Swift 6** language mode with complete data-race checking (`swift-tools-version:6.2`, so Swift 6.2 or later builds it), Swift Concurrency with Approachable Concurrency ([Concurrency](#concurrency)), `@Observable` for state. The project is a Swift Package, so the **Command Line Tools are enough to build and test** (against the macOS 26 SDK when theirs is macOS 27, §13): the tests use Swift Testing, which ships with them as well as with Xcode.

Principles:

- **One source of truth for meetings.** `MeetingStore` owns `[Meeting]`; everything else reads from it.
- **Scheduling is pure.** `AlertScheduler` takes `(meetings, alertStates, leadTime, isPaused, now)` and returns the next thing to do. No timers, no windows. Fully unit-testable. The notification, the second kind of alert, is planned by the same scheduler with its own lead time and states (`NotificationSchedule`, §5).
- **Presentation is pure too.** What the menu bar item says, what the panel lists, the alert's countdown wording, resolved colors and screens, and what the Settings pop-ups show, what a notification says and which buttons it offers, and the Notification box's status line are computed in `JoinCore` (`MenuBarPresenter`, `PanelPresenter`, `LocationFormatter`, `AlertCountdown`, `AlertAppearance.palette`, `AlertScreens`, `SettingsOptions`, `MinutesChoice`, `ColorChoice`, `AlertColorRow`, `UpdateCopy`, `NotificationContent`, `NotificationStatus`) from plain values and a `now`. The SwiftUI views only lay the results out. Whether a release is an update, when to check for one and what a check's result changes are decided there too (`UpdateCheck`, `UpdateCheckOutcome`).
- **Side effects live at the edges.** `AlertCoordinator` owns the timer and calls the scheduler, and `NotificationCoordinator` does the same for notifications, posting them through `NotificationCenterClient`; `AlertWindowController` and `StatusItemController` own windows; `ReleaseFeed` and `UpdateInstaller` do the update's networking and file work (§14).
- **Calendar backend is swappable.** `CalendarService` is a protocol. Besides EventKit there is a fixture implementation for checking the UI (§12), and a direct Google API implementation can be dropped in later. `ReleaseFeed` works the same way for updates: GitHub, or a fixture. So does `NotificationCenterClient` for notifications: macOS's notification center, or a fixture's stand-in that never touches it (§12).

### Concurrency

Every target, the tests included, builds in the Swift 6 language mode, with complete data-race checking, and with the two upcoming features that make up Approachable Concurrency: `NonisolatedNonsendingByDefault` (a nonisolated `async` function runs on its caller's actor; only a `@concurrent` one leaves it) and `InferIsolatedConformances` (a main-actor type's conformances are isolated to the main actor). Nothing is silenced: there is no `@preconcurrency`, and the one `@unchecked Sendable` (`Download`, below) says why.

- **The app (`Join`) is on the main actor by default** (`.defaultIsolation(MainActor.self)` in `Package.swift`). App state, views, windows and controllers need no `@MainActor`; a declaration that something else runs says `nonisolated`, with the reason beside it:
  - **Drawing.** AppKit runs an image's drawing handler, and asks a dynamic `NSColor` for its value, on whatever thread is drawing (Apple's documentation says so for `NSImage(size:flipped:drawingHandler:)`). Neither API marks its closure `@Sendable`, so the compiler can't tell: a closure written in main-actor code is main-actor isolated, and Swift 6 checks that at run time, reporting a data race when AppKit calls it from another thread. So the code that makes those closures is nonisolated: `PanelColors`, `SettingsPalette`'s dynamic colors, the `Color`/`NSColor`/`RGBA` conversions, `StatusItemImages`' ring and pill drawing and the pill's label color, `MenuBarPanelWindow`'s mask image and `SettingsSwatchDot`'s drawing.
  - **Layout.** SwiftUI's `Layout` is `Sendable` and may run off the main actor, so `SettingsFlowLayout` is nonisolated, and so is the layout value it reads, `SettingsFlowFill`.
  - **Shapes.** SwiftUI's `Shape` is `Sendable` with nonisolated requirements, and `path(in:)` may run off the main actor, so `PanelStripes` is nonisolated. The macOS 26 SDK strips main-actor inference from shapes (`_RemoveGlobalActorIsolation`); the macOS 27 SDK (Xcode 27's default) doesn't, and there a main-actor shape's conformance is rejected.
  - **Menus.** `ClosureMenuItem` is nonisolated like `NSMenuItem`, whose initializers it overrides; AppKit sends its action on the main thread, so `run` calls its `@MainActor` handler through `MainActor.assumeIsolated`, which traps rather than races if that ever changes.
  - **Updates.** `ReleaseFeed` and `UpdateInstalling` are nonisolated protocols, with `Sendable` value types behind them (and `FixtureReleaseFeed`, an actor). `UpdateInstaller.prepare()` and `install()` are `@concurrent`, so hashing, unzipping, signature checks and the swap run off the main actor; `UpdateChecker` awaits them from it. `Download`, the `URLSession` delegate that streams the update to disk, is nonisolated and `@unchecked Sendable` because its state is only touched on its session's serial delegate queue. The app's log categories (`Logger.updates`, `.calendar`, `.alerts`, `.notifications`, `.fixture`, `.settings`, each declared once in `Logger+Join.swift`, under the `com.poliuk.join` subsystem) are nonisolated `static let`s, so the installer and the notification center client log from off the main actor. JoinCore can't see the app's extension, so `Preferences` keeps its own file-private logger, category `preferences`, in `Preferences.swift` (§3).
  - **Notifications.** UserNotifications has no `Sendable` annotations and calls its delegate on its own queue, not the main thread. `NotificationCenterClient` is a nonisolated protocol that returns only `Sendable` values (`NotificationPermission`, identifiers) and takes JoinCore's `NotificationContent`; `SystemNotificationCenter` asks for `UNUserNotificationCenter.current()` on each call rather than keeping it, and reads settings and delivered notifications through `withCheckedContinuation`, mapping them inside the completion handler. `FixtureNotificationCenter` is the fixture run's stand-in, which never touches the real center, and `UnavailableNotificationCenter` a build without an app bundle's (§5). `NotificationResponder`, the delegate, is set in `applicationWillFinishLaunching`, before launch finishes, so a response that launches Join! reaches it, and only in a real run (the stand-in sets none). It's a nonisolated `Sendable` class: `willPresent` answers at once, the `async` `didReceive` reads the response into a `Sendable` `NotificationReply` and `await`s a `@MainActor` closure (`NotificationCoordinator.handle`), so macOS's completion runs after the handling, and the time of the last response sits behind an `OSAllocatedUnfairLock`, because the reopen handler on the main thread may read it before that hop has run.
- **`JoinCore` has no default isolation.** Its rules are nonisolated, so callers decide where they run. Every public value type says `Sendable` (Swift never infers it for a public type); only the caseless enums that namespace its functions and constants (`PanelPresenter`, `UpdateCopy`, …), which have no values to send, don't. It has no mutable globals: its statics are `let`s of `Sendable` types, its one file-scope global is `Preferences`' `let logger` (a `Logger`, which is `Sendable`), and it has no `async` code. `Preferences`, which wraps `UserDefaults` for the UI to observe, is the one `@MainActor` type, and its constants aren't isolated: the defaults (`defaultLeadTime`, `defaultNotificationLeadTime`, `defaultSnoozeDurations`, `defaultAutoCloseAfter`) are `nonisolated`, and `Preferences.Keys`, a nested type, doesn't take the class's isolation, so code off the main actor (a test, say) reads them without `await`. `Keys` is internal: the app goes through the properties, which observe, clamp and check what's written, never `UserDefaults` directly.
- **Async work stays on the main actor unless it's heavy.** `GitHubReleaseFeed.latestRelease()`, `MeetingStore.start()` and the notification center client's calls run there and await system APIs (`URLSession`, EventKit's access request, UserNotifications) that wait off it. Only the installer's two steps and `UpdateInstaller.removeLeftovers()` (the file work that clears what a crashed install left, which `UpdateChecker.start(now:)` starts in a utility-priority task at launch) are `@concurrent`. The install's progress comes back through one `AsyncStream` that keeps only the newest report, drained by a child task of the install, so reports arrive in order and none outlives it.
- **System callbacks state their isolation.** Notification, timer and observation blocks are `@Sendable`, so the compiler doesn't know they run on the main thread:
  - **`MainActor.assumeIsolated`**, which runs the work at once, in delivery order, and traps if it's ever called off the main thread, for every callback that the main queue or the main run loop delivers: the notification observers registered with `queue: .main` (wake in `AppModel` and `MeetingStore`, `EKEventStoreChanged` in `EventKitCalendarService`, screen changes in `AlertWindowController`, `StatusItemController`'s, Join! becoming active and Settings becoming key in `NotificationCoordinator`, the fixture's script hooks in `AppDelegate`), the timers on the main run loop (`AppModel`'s 30-second clock, `MeetingStore`'s safety net, `AlertCoordinator`'s heartbeat and auto-close, `NotificationCoordinator`'s heartbeat, the fixture's two-hour limit), and the event monitors (the panel's and the alert's). A timer made after an `await` names `RunLoop.main` rather than relying on `scheduledTimer`'s current run loop. The auto-close in particular must not wait: a dismissal left for later could close the next alert instead.
  - **`Task { @MainActor in … }`** only in `observeChanges` (`Observation+Changes.swift`): `withObservationTracking`'s `onChange` fires before the change, on whatever thread makes it, so it hops, which also lets the new value land before it's read again. And in `NotificationResponder`'s `openSettingsFor`, which macOS calls on its own queue and which has no `async` form.
  - The fire timers (the full-screen alert's and the notification's) are `DispatchSource`s on the main queue, called on the main thread.

## 3. Data model

```swift
struct Meeting: Identifiable, Hashable, Sendable {
    /// eventIdentifier + start timestamp — recurring events share an
    /// eventIdentifier, so the occurrence start is part of the id.
    let id: String
    var title: String
    var start: Date
    var end: Date
    var isAllDay: Bool
    var calendarID: String
    var calendarTitle: String
    var calendarColor: RGBA              // no AppKit types in JoinCore
    var location: String?
    var notes: String?
    var url: URL?
    var myStatus: ParticipationStatus    // accepted (also organized events, and events without attendees on calendars you can edit), tentative, declined, unknown (not answered, not invited, or someone else's calendar)
    var hasParticipants: Bool            // someone other than you is on it (§4); false for focus time and reminders to yourself
    var joinURL: URL?                    // filled by MeetingLinkDetector
    var isOutOfOffice: Bool              // filled by OutOfOfficeDetector (§9a)
    var seriesID: String?                // the repeating event it's an occurrence of (its eventIdentifier); nil for a one-off (§7)
}

enum AlertState: Equatable {   // one map per kind of alert: alertStates, notificationStates (§5)
    case pending                 // will fire at start - leadTime
    case snoozed(until: Date)
    case showing
    case dismissed               // no more alerts for this occurrence
}

enum PauseState: Codable {       // set from the panel's bell menu; pauses both kinds of alert (§5)
    case active
    case until(Date)             // "1 hour", "until tomorrow"
    case indefinitely            // "until I resume"
}

enum EventVisibility: String, CaseIterable, Comparable {   // stored as its raw value (§4)
    case showAndAlert            // "Show and alert": like any other event
    case listOnly                // "Show in the list only": the panel's lists, nothing else
    case exclude                 // "Exclude": left out everywhere; exclude < listOnly < showAndAlert
}

final class Preferences {                  // @Observable, persisted in UserDefaults
    var leadTime: TimeInterval = 180       // always whole minutes; kept while Alert me is Never
    var fullScreenAlertsEnabled = true     // false = Alert me › Never: no full-screen alerts (§5)
    var notificationsEnabled = false       // false = Notify me › Never, the default: no notifications, macOS not asked (§5)
    var notificationLeadTime: TimeInterval = 300   // whole minutes; kept while Notify me is Never; independent of leadTime
    var notificationPlaysSound = true      // Play sound: macOS's notification sound, or none
    var snoozeDurations = SnoozeDurations(first: 60, second: 300)   // two fields, so always two; stored as [60, 300];
                                           //   shared: the full-screen alert's buttons and the notification's actions
    var alertScreens: AlertScreens = .all  // .all, .main, .secondary, .pointer (§6)
    var autoCloseEnabled = true
    var autoCloseAfter: TimeInterval = 15 * 60   // never under a minute, set or loaded
    var soundName: String? = nil
    var soundRepeats = false
    var enabledCalendarIDs: Set<String>?   // nil = never chosen → all
    var eventsWithoutParticipants: EventVisibility = .showAndAlert   // §4
    var menuBarDisplay: MenuBarDisplay = .time   // §7; stored as two switches, menuBarShowsNextEvent and menuBarShowsEventTitles
    var outOfOfficeEvents: EventVisibility = .listOnly   // §4, §9a
    var outOfOfficeKeywords: [String]
    var appearance: AlertAppearance
    var customAppearance: AlertAppearance?   // the Custom style card's look (§8); nil until there's one
    var startingSoonPill: StartingSoonPill
    var panelListFilter: PanelListFilter = .week   // the panel's Today | 7 Days switch
    var dismissedEvents = DismissedEvents()   // occurrences dismissed from the panel (§7); not a setting
    var checksForUpdates = true            // the daily update check (§14); Check Now works either way
    var lastUpdateCheck: Date?             // the last successful check; nil = never
    var offeredUpdateVersion: AppVersion?  // the version the last successful check offered; nil = none; stored as "1.1.0"
    var unsupportedUpdate: UnsupportedUpdate?   // a release this macOS can't run; nil = none
}

struct UnsupportedUpdate: Codable, Equatable {  // saved as JSON: {"version":"2.0.0","minimumSystem":"15.0"}
    let version: AppVersion           // the release Install found this Mac can't run (§14); coded as its "2.0.0" string
    let minimumSystem: String         // its LSMinimumSystemVersion
}

struct DismissedEvents: Codable, Equatable {  // saved as JSON (§7); 1.2.0's plain object of id → end still reads
    var occurrences: [String: Occurrence]     // Meeting.id → an occurrence dismissed on its own
    var seriesRules: [String: [SeriesRule]]   // Meeting.seriesID → All Future Events, usually one rule
    var exceptions: [String: Occurrence]      // Meeting.id → an occurrence restored on its own inside a rule

    struct Occurrence: Codable, Equatable {
        var start: Date?              // nil in entries saved by 1.2.0, until pruning finds the event
        var end: Date                 // when the entry expires
        var seriesID: String?
    }

    struct SeriesRule: Codable, Equatable {
        var from: Date                // the start of the occurrence All Future Events was chosen on
        var until: Date?              // the start of a later one Restore All Future Events was chosen on
    }
}

struct StartingSoonPill: Codable, Hashable {  // saved as JSON; missing keys fall back to the default
    var minutes = 5                   // 1...60; when the menu bar pill and the panel's starting-soon card appear
    var fill: RGBA?                   // nil = the system accent color
    var text: RGBA?                   // nil = Automatic: white unless the fill shown gives it < 3:1, then near-black;
                                      //   Settings no longer sets it, only shows one an earlier build stored
}

struct AlertAppearance: Codable, Hashable {   // saved as JSON with "version": 3
    var blurMode: BlurMode            // .dark, .light (.none only from old saves)
    var tint: RGBA?                   // nil = no tint
    var tintStrength: Double          // 0...1, kept while the tint is off
    var textColor: RGBA?              // nil = Automatic (Settings' Event text)
    var join: AlertButtonColors
    var dismissAndSnooze: AlertButtonColors
    static let `default` = AlertAppearancePreset.dark.appearance
}

struct AlertButtonColors: Codable, Hashable {
    var text: RGBA?                   // nil = Automatic; only an earlier build stores one (a legacy Text row, §8)
    var fill: RGBA?                   // nil = Automatic (Orange for Join)
    var fillOpacity: Double           // scales the fill; Join 0.4...1 (Settings sets 1), others 0...1
}
```

Launch at login is not a preference: it is read from and written to `SMAppService` directly. The pause state is stored by `AlertCoordinator` next to the alert states, and pauses both kinds of alert; the notification's own per-meeting states are stored by `NotificationCoordinator` under `notificationStates`, in the same shape (§5). The time of the last failed update check isn't stored at all: `UpdateChecker` keeps it in memory (§14). Setting `offeredUpdateVersion` or `unsupportedUpdate` to nil removes its key, and a stored value that can't be read loads as nil (an unsupported update whose version doesn't parse included). Likewise an empty `dismissedEvents` removes its key, and one that can't be read loads as empty. Every setting stored as JSON (the looks, the pill, the dismissed events, the unsupported update) goes through two helpers: one that can't be read loads as its default and is logged (`com.poliuk.join`, category `preferences`, at error level, the key public and the decoding error private, since its coding path can name event ids); one that can't be encoded (a NaN in a color, say) leaves what's stored as it was, and is logged the same way. Fixture runs keep `lastUpdateCheck`, `offeredUpdateVersion` and `unsupportedUpdate` in memory too, unless `JOIN_FIXTURE_UPDATE=live` (§12).

`RGBA` is a small Codable sRGB struct, so calendar colors and the theme round-trip to JSON. It also holds the color math the appearance needs: hex parsing, compositing (`composited(over:)`, `mixed(with:amount:)`), WCAG relative luminance and contrast ratio, and `mostLegible(of:_:)`.

## 4. Calendar integration (EventKit)

**Permission.** `EKEventStore.requestFullAccessToEvents()` (macOS 14 API). `Info.plist` needs `NSCalendarsFullAccessUsageDescription`. Entitlement `com.apple.security.personal-information.calendars` if sandboxed (recommended; nothing here needs to escape the sandbox).

**Calendars.** `store.calendars(for: .event)` grouped by `calendar.source.title` (e.g. a work account and a personal account appear as separate groups). Calendar colors are converted to `RGBA` so `Meeting` stays free of AppKit types. The Calendars pane (§8) writes `Preferences.enabledCalendarIDs`.

**Fetching.** Window is `now − 1 h … now + 7 days`:

```swift
let predicate = store.predicateForEvents(withStart: from, end: to, calendars: enabled)
let events = store.events(matching: predicate)   // recurrences already expanded
```

Mapping rules:

- Skip `isAllDay`.
- Skip when the current user's `participantStatus == .declined` (find the `EKParticipant` with `isCurrentUser`).
- Skip `status == .canceled`.
- Tentative and unknown are included: you can't know whether the user will attend, so alerting is the safe default.
- `seriesID` is the event identifier when the event repeats: `hasRecurrenceRules`, or `isDetached` (an occurrence edited on its own, which still belongs to the series). Every occurrence of a series shares that identifier, the part of `Meeting.id` before "@". nil for a one-off. Dismissing all future events of a series goes by it (§7).
- `hasParticipants` is true when someone other than you is on the event: an attendee whose `isCurrentUser` is false, or an organizer who isn't you. A booked room or resource doesn't count. An event with nobody else on it (no attendees and no organizer, or only you and rooms) has no participants: focus blocks, reminders and holds you made for yourself, and most holiday and subscribed calendar blocks. Such events are still mapped; `MeetingStore` decides whether they're used.

After fetching, `MeetingStore` fills `joinURL` (§9) and `isOutOfOffice` (§9a) on each meeting, then filters them (below). The order matters: the filter reads `isOutOfOffice`.

**Which events are used.** Settings › General › Events (§8) has a choice, an `EventVisibility`, for each of two kinds of event: events with no participants (`Preferences.eventsWithoutParticipants`, **Show and alert** by default) and out-of-office events (`Preferences.outOfOfficeEvents`, §9a, **Show in the list only** by default). `MeetingFilter.visibility(of:eventsWithoutParticipants:outOfOfficeEvents:)` (JoinCore) gives a meeting's choice: the one for its kind; for an event of both kinds, the one that shows less (`min`, since `exclude < listOnly < showAndAlert`); and `.showAndAlert` for any other event. `MeetingStore.meetings` keeps the visible ones (`MeetingFilter.visible`: the choice isn't Exclude) and `alertableMeetings` the alertable ones (`MeetingFilter.alertable`: the choice is Show and alert, less the occurrences dismissed from the panel, §7), always a subset. Everything reads from those two:

| Choice | Panel lists | Hero card, menu bar item, alerts (full-screen and notification) |
|---|---|---|
| Show and alert | yes | yes |
| Show in the list only | yes | no |
| Exclude | no | no |

So Exclude leaves an event out everywhere, as if its calendar were unchecked but decided per event. Out-of-office rows stay striped and muted whatever the choice (§7); an event with no participants is drawn like any other row, with its Join or Directions button. The defaults keep what 1.1 did out of the box. Changing either choice refetches (below), so excluded events come back as soon as they're shown again. A Show and alert event dismissed from the panel (§7) is treated like Show in the list only until it ends or is restored, except that its row is marked dismissed and offers Restore.

**Staying fresh.** Refetch on:

- `NSNotification.Name.EKEventStoreChanged` (fires when the system calendar database changes, including after a Google sync),
- `NSWorkspace.didWakeNotification`,
- a change to `enabledCalendarIDs`, `eventsWithoutParticipants`, `outOfOfficeEvents` or `outOfOfficeKeywords`,
- **Refresh Calendars** in Settings,
- a 15-minute safety-net timer.

Each refetch replaces `MeetingStore.meetings`, records `lastRefreshed` (for the "Updated just now" label in Settings) and prunes the dismissed events (§7). Both alert coordinators observe `alertableMeetings`, so they re-plan (§5). Google sync latency itself is governed by Calendar.app › Settings › Accounts › Refresh Calendars; the README tells users to set it to "Every minute" or "Every 5 minutes".

**Alternative backend (P2, not built now).** `GoogleCalendarService: CalendarService` would use OAuth 2.0 with PKCE via `ASWebAuthenticationSession` and a loopback redirect, `calendar.readonly` scope, tokens in Keychain, `events.list` with `syncToken` every 60 s, and `conferenceData.entryPoints` for join links. Blocked on creating a Google Cloud project and going through OAuth verification.

## 5. Alert scheduling

The heart of the app. Kept pure so it can be tested exhaustively.

```swift
struct AlertPlan: Equatable {
    var fireAt: Date
    var meetings: [Meeting]      // ≥1; several meetings may share a fire time
}

enum AlertScheduler {
    /// Returns the next alert to fire, or nil.
    static func nextPlan(meetings: [Meeting],
                         states: [Meeting.ID: AlertState],
                         leadTime: TimeInterval,
                         isPaused: Bool,
                         now: Date) -> AlertPlan?
}
```

Rules:

1. For each meeting with state `.pending`: `fireAt = start − leadTime`. If `fireAt < now` but `end > now` (we missed it: app launched late, Mac was asleep) → fire **now**, unless the meeting already started more than 5 minutes ago (`lateAlertGrace`), in which case it is skipped: alerting for a meeting you are presumably already in is noise.
2. `.snoozed(until)` → `fireAt = until`, again clamped to `now` if in the past, and dropped once `end < now`.
3. `.showing` and `.dismissed` produce nothing.
4. Meetings whose `fireAt` fall within 1 second of the earliest one are grouped into a single `AlertPlan`, so two back-to-back meetings produce one alert listing both instead of two stacked windows.
5. If `isPaused`, return nil. `AlertCoordinator` passes true while alerts are paused (`PauseState.isPaused(at: now)`, both kinds) or full-screen alerts are turned off (**Alert me** set to **Never**, `Preferences.fullScreenAlertsEnabled` false). When a pause ends, or a time is picked again after Never, rule 1 applies as usual: a meeting that is about to start, or started less than 5 minutes ago, alerts right away.

The meetings passed in are `MeetingStore.alertableMeetings`: those whose Events choice is Show and alert (§4), less the ones dismissed from the panel (§7). `AlertCoordinator` observes that list, so dismissing an event re-plans at once: nothing fires for it, pending or snoozed, and an alert on screen drops it, closing if it was the only meeting. Its `AlertState` is left as it was, so **Restore** re-plans with it under rules 1 and 2, as when a pause ends: a pending alert fires at its time, or at once if that has passed, unless the meeting started more than 5 minutes ago; a snoozed one at its snooze time, or at once if that has passed. One that was on screen when the event was dismissed stays `.showing` and doesn't come back. The alert's own **Dismiss** (`.dismissed`, below) is a different thing: it closes the alert, and the event keeps the menu bar item and the panel's card.

`AlertCoordinator` (side effects):

- Holds one `DispatchSourceTimer`. On every re-plan it cancels and re-arms the timer for `plan.fireAt`, with 0.5 s leeway.
- Also runs a 30-second **heartbeat** that re-plans and fires anything overdue. This catches the cases where a one-shot timer silently fails: system sleep, clock/timezone change, the process being suspended by App Nap (which we also disable via `ProcessInfo.beginActivity(.userInitiatedAllowingIdleSystemSleep)` while an alert is pending within 5 minutes). The heartbeat is also what ends an expired timed pause.
- Schedules nothing until `start()` is called. Fixture runs (§12) never call it, so they can't alert.
- On fire: mark meetings `.showing`, ask `AlertWindowController` to present on the screens chosen in `Preferences.alertScreens`, play the sound, start the auto-close timer if configured.
- User actions from the alert: Dismiss → `.dismissed`; Snooze(d) → `.snoozed(until: now + d)`; **At \<time\>** → `.snoozed(until: start)`, or `.dismissed` if the meeting has already started; Join → open URL then `.dismissed`. Since 1.3.0 each is an `AlertResponse`, whose `state(of:answering:meeting:now:)` (JoinCore) gives the new state of either kind of alert: Join also finishes that meeting's notification (`didAnswer`, which `AppModel` hands to `NotificationCoordinator.fullScreenAnswered`), while Dismiss, the auto-close, Snooze and At \<time\> leave the notification alone (Notifications, below). On an alert listing several meetings, Join is Join for the meeting it names and a close for the others.
- `AlertState`s are persisted (`UserDefaults`, each with the meeting's end as expiry, pruned when expired) so a relaunch during a snooze doesn't re-alert or lose the snooze.
- **Pause.** It pauses both kinds of alert: `NotificationCoordinator` reads `pauseState` from here (below). `pause(_ option: PauseOption)` turns "1 hour", "until tomorrow" (local midnight) or "until I resume" into a `PauseState`; `resume()` sets `.active`. The state is saved as JSON under `pauseState`, so "Pause until tomorrow" survives a relaunch. A timed pause that has run out collapses to `.active` on load and on the next re-plan.
- **Never.** `AlertCoordinator` re-plans when `fullScreenAlertsEnabled` changes, as it does for the lead time. Never is modelled as its own Bool, not a lead time, so `leadTime` keeps the last time chosen and the scheduler stays unaware of it beyond `isPaused` (rule 5). Picking Never cancels what's pending: nothing fires, snoozed alerts included, until a time is picked again. An alert already on screen stays until it's closed, since re-planning waits while one shows (below); the lead chose this, for least surprise. The menu bar item, its starting-soon pill and the panel don't depend on it, and the menu bar doesn't show the paused bell.
- One alert at a time: while an alert is on screen, nothing else fires; the next plan is computed when it closes. The rule is the full-screen alert's own: notifications never wait for it (below).
- If a meeting is edited (start moves) its `id` changes → new occurrence, state resets to `.pending`. Cancelled meetings disappear from the store; if their alert is showing, the window closes.
- `showDemoAlert()` presents a fake meeting starting 3 minutes out (on a whole second, so the countdown starts at 3:00), "Hello, I’m a demo event" (`MenuBarPresenter.demoEventTitle`), on the Work calendar in Conference Room A with a link (`DemoEvent`, shared with Test Notification), for **Test Full-Screen Alert** on the Alerts and Appearance panes (**Show Demo** until 2026-10-19; the `showDemoAlert` hook kept its name). It works while paused and with **Alert me** set to **Never**. Join opens the demo event's link (a sample Google Meet link), as a real alert's does, so the test tries it end to end (the user: "the 'Test notification' should include a link to the videocall", 2026-10-19, applied to both tests); every button closes it. It is refused, and the Settings button is disabled, while a real alert is on screen (`isAlerting`); a real alert that fires during a demo replaces it.
- `willPresentAlert` runs right before any alert (real or test) is presented. The app uses it to close the menu bar panel, including a header menu that is open, so the panel can't take keyboard focus back from the alert.

### Notifications

Since 1.3.0 a meeting can also get a macOS notification, the second kind of alert (`AlertKind.notification`). The user asked for it and chose Direction A, "One Alerts tab", on 2026-10-16 ([PRODUCT_BRIEF](PRODUCT_BRIEF.md) §9): each kind has its own time or Never on the Alerts pane (§8), **Alert me** for the full-screen alert and **Notify me** for the notification, and they share the pause (`AlertCoordinator.pauseState`), the panel's dismissals and the Events choices (these two through `alertableMeetings`), and the two snooze durations. Notify me is Never by default, for new installs and upgrades alike, so nothing changes until the user picks a time.

**Planning.** `NotificationSchedule.nextPlan` (JoinCore) is `AlertScheduler.nextPlan` with Notify me's lead time (`notificationLeadTime`), the notification's own states, and `isPaused` true while Notify me is Never (`notificationsEnabled` false) or alerts are paused. The rules above hold as they are: the late grace after sleep, a late launch, the end of a pause or a Restore; snoozes; grouping within a second. The full-screen alert's lead time, states and Never play no part, and neither does its one-alert-at-a-time rule, so a notification is never held back while a full-screen alert is up.

`NotificationCoordinator` (main actor, owned by `AppModel`, beside `AlertCoordinator` rather than inside it):

- **Posts at fire time.** Join! posts each notification itself when its plan is due, with no trigger, so macOS delivers it at once. Nothing is scheduled with macOS ahead: a pause, Never, the Events choices, panel dismissals, calendar edits and cancellations take effect at once, and a quit or deleted Join! leaves no stale reminders. The cost is that nothing comes while Join! isn't running, as for the full-screen alert. Like `AlertCoordinator` it has its own `DispatchSourceTimer` (0.5 s leeway), a 30-second heartbeat that re-plans, and the App Nap guard while a notification is due within 5 minutes. It re-plans when `alertableMeetings`, Notify me's time or Never, or `AlertCoordinator.pauseState` change.
- **One per meeting, sent once.** Everything due goes out at once, each meeting with its own notification, so meetings at the same time each get one, grouped by macOS on the `meetings` thread. The request's identifier is `meeting:<occurrence id>` (`NotificationIdentifier`). Once sent, the meeting's state is `.dismissed` (`NotificationSchedule.sentState`), so it isn't sent again, not even when Notify me's time changes. The states are saved as `AlertStateRecord`s under `notificationStates`, each expiring at the meeting's end and pruned like `alertStates`.
- **Content** (`NotificationContent`, JoinCore): the title is the event's (macOS shows Join!'s name and icon above it); the subtitle its time range (`MeetingTimeFormatter.timeRange`, "10:00 – 10:30 AM"); the body its calendar's name, then its location as the full-screen alert shows it (`LocationFormatter.alertLocation`), "Work · Conference Room A", either alone when the other is missing; the test notification's body says what it is instead, "This is a test notification." (`DemoEvent.notificationBody`). Only clock times, never "Starts in 3 min": a delivered notification can't update, and macOS adds its own "now" or "5m ago". Previews follow the user's Show previews setting. The meeting's id, link, start and end ride in `userInfo` as strings (`NotificationPayload`), so a response can be handled before the calendar has been read, as when the response launches Join!.
- **Sound.** **Play sound** (`notificationPlaysSound`) gives macOS's default notification sound, or none. The full-screen alert's list of named sounds isn't offered, since macOS doesn't reliably play them for notifications, and Join! doesn't play a sound of its own, which would ignore a Focus. A notification is silent while its meeting's full-screen alert is on screen (`NotificationSchedule.playsSound`), and the coordinator lets `AlertCoordinator` re-plan just before sending, so a full-screen alert due at the same moment goes up first: the two sounds never overlap.
- **Active, never Time Sensitive.** The interruption level is `.active`. Time Sensitive needs the restricted `com.apple.developer.usernotifications.time-sensitive` entitlement, which an ad-hoc signature can't carry; claiming it gets the app killed at launch. So during a Focus macOS holds Join!'s notifications unless the user allows Join! in it, and by default it holds them while the display is mirrored or shared (§10). Join! can detect neither. The full-screen alert ignores both, and the Notification box's footnote says so (§8).
- **Actions** (`NotificationCategory`, `NotificationAction`). macOS fixes a category's buttons and looks the category up when it shows a notification, so there are four categories, `meeting.join.atStart`, `meeting.join`, `meeting.atStart` and `meeting`, registered together (`NotificationCategory.all`) at start and again whenever `snoozeDurations` changes, which reaches notifications already delivered too. **Join** comes first, since a banner shows only the first two actions, and only when there's a link; then **Snooze 1 min** and **Snooze 5 min**, the shared durations, each once (`AlertCountdown.snoozeChoices`); then **At event start**, only while the start is more than a second ahead. At most four. The identifiers carry what the action does: `join`; `snooze.<seconds>`, in the whole minutes its title reads, so a notification delivered before the durations changed still snoozes for what its button said; `atEventStart`. No action brings Join! to the front: Join opens the link from the background, as the full-screen alert's Join does while Join! isn't active. There's no Dismiss action: macOS's own close button closes the notification and changes nothing else, since a sent notification is already done.
- **Responses** (`handle`). `AlertResponse(notificationActionIdentifier:)` reads the action, and `AlertResponse.state` decides for both kinds. **Join** opens the link and finishes both: the notification's state and the full-screen alert's become `.dismissed` (`AlertCoordinator.notificationAnswered`), so neither comes, and a full-screen alert on screen drops the meeting, closing if it was the only one. **Snooze** (`.snoozed(until: now + d)`) and **At event start** (`.snoozed(until: start)`, or `.dismissed` once the meeting has started) act on the notification only: it's withdrawn and sent again then, under the same identifier, so it replaces itself and moves to the top, while the full-screen alert still comes at its own time. So a gentle-then-loud setup, a notification 5 minutes before and the full-screen alert at the start, works as expected. The other way round, Join on the full-screen alert withdraws the meeting's notification and drops a pending or snoozed one (`fullScreenAnswered`); its Snooze, Dismiss and auto-close leave the notification alone.
- **A click does nothing.** A click on the notification itself (`UNNotificationDefaultActionIdentifier`) maps to no response, so Join! does nothing, by the user's choice (2026-10-16); the notification goes away, as macOS does with a clicked one. macOS may also send Join! a reopen event with the click, and a reopen opens Settings (§8), so `applicationShouldHandleReopen` ignores a reopen within a second of the last response (`NotificationSchedule.reopenGrace`, `ignoresReopen`). The responder records that time as the response arrives, before its hop to the main actor ([Concurrency](#concurrency)). Any other reopen opens Settings as before.
- **Withdrawals.** A delivered notification is removed once its meeting is no longer alertable (dismissed from the panel, cancelled, moved, which gives it a new occurrence id, or now Show in the list only or Exclude) or has ended (`NotificationSchedule.withdrawals`): when `alertableMeetings` changes, on the heartbeat, and whenever the permission is read again, which at launch clears what an earlier run left for meetings now gone. Only once the calendar has been read (`lastRefreshed`), or every meeting would look gone, but whatever the permission read last says: a grant made in System Settings isn't seen until Join! is next active, yet notifications are delivered meanwhile, and with nothing delivered there's nothing to withdraw. The test notification is left for the user to close. A pause or Never withdraws nothing: they only stop what's still to come. **Restore** from the panel re-plans as for the full-screen alert: a notification not sent yet, or snoozed, comes at its time, or at once within the late grace; one already sent doesn't come back.
- **Permission.** Join! asks macOS (`requestAuthorization` with `.alert`, `.sound` and `.providesAppNotificationSettings`; no badge, since Join! has no Dock icon, and no quiet provisional mode) only when Notify me first leaves Never or Test Notification is first clicked, and only while nothing is decided (`NotificationPermission.needsAsking`, on a fresh read): macOS prompts once and answers later requests with the stored choice. It never asks at launch, so an upgrade never prompts. For up to a minute after asking nothing is sent, so a notification due at once comes after the user answers rather than failing before; then the heartbeat sends what's due, whatever the answer. Nothing is sent either while Notify me has a time whose ask hasn't started (`NotificationSchedule.holdsSending`): a preset picked from Never writes the time before Notify me, so the re-plan for the time, or the heartbeat's, can run before the ask, and leaving Never with any preset or Custom… is covered. While notifications aren't allowed, a due notification is still marked sent and posting fails, which is logged (`Logger.notifications`), so the ones due meanwhile don't come later. The permission (`NotificationPermission`: not determined, denied, or allowed, with whether it reaches the screen and whether macOS's sound for Join! is on) is read at start, after asking, when Join! becomes active and when Settings becomes key, since macOS reports no changes; it drives the status line and Test Notification (§8). `.providesAppNotificationSettings` lets System Settings › Notifications › Join! offer a link back to Join!, which reaches the responder's `openSettingsFor` and opens Settings on Alerts.
- **While Join! is active.** The responder's `willPresent` answers `[.banner, .list, .sound]`, so a notification shows even while Settings is the frontmost window.
- **Test Notification** (`sendDemoNotification()`; **Send Demo Notification** until 2026-10-19) posts the demo event's notification (`NotificationContent.demo`, from `DemoEvent`, identifier `demo`, with the body "This is a test notification.") at once, while paused and with Notify me on Never too, as Test Full-Screen Alert works, following Play sound and the snooze durations. Its first click asks macOS when nothing is decided yet; nothing is sent while notifications are denied. Its **Join** opens the demo event's link, as a real notification's does (2026-10-19); its other actions only close it.
- **Fixture runs** share the app's bundle id, so they never touch the real notification center: no prompt, no posting, no responder, no withdrawals. `AppModel` gives the coordinator `FixtureNotificationCenter`, whose permission comes from `JOIN_FIXTURE_NOTIFICATIONS` (§12). `start()` still reads it, for the status line, and follows Notify me, but plans and sends nothing.
- **A build without an app bundle** (`swift run`, `.build/debug/Join`) can't use `UNUserNotificationCenter`, which raises in such a process, so `AppModel` gives it `UnavailableNotificationCenter` (only a run from `Join.app` gets the real one): never allowed, and nothing is asked, sent, removed or logged, as such a build's update checker never checks.

## 6. Alert window (AppKit)

One `AlertWindow` (an `NSPanel`) per target screen. `Preferences.alertScreens` picks them, through `AlertScreens.targetIndices(screenCount:pointerScreenIndex:)` in JoinCore, a pure function over indices into `NSScreen.screens`; `AlertWindowController.targetScreens(for:)` hands it the screen count and the index of the screen under the mouse pointer, and maps the indices it returns back to screens. Index 0 is the main screen: the one with the menu bar, which macOS calls the main display (`NSScreen.screens.first`). `.all` covers every screen, `.main` the main one, `.secondary` (new in 1.2.0) every other one, and `.pointer` the one under the pointer when the alert fires. The alert never silently vanishes: with a single screen `.secondary` falls back to the main one, and so does `.pointer` when the pointer is on no screen. Before 1.2.0, `.main` was `NSScreen.main`, the screen with the key window, which can be a secondary one while Join!'s Settings window sits there, and `.pointer` fell back to it. The first window becomes key and the others are ordered front. The windows are recreated on `NSApplication.didChangeScreenParametersNotification` (display hot-plug while showing), so unplugging the last secondary screen moves a Secondary screen only alert to the main one.

```swift
let panel = NSPanel(contentRect: screen.frame,
                    styleMask: [.borderless, .nonactivatingPanel],
                    backing: .buffered, defer: false)
panel.level = .screenSaver                        // above menu bar and full-screen apps
panel.collectionBehavior = [.canJoinAllSpaces, .fullScreenAuxiliary, .stationary, .ignoresCycle]
panel.isFloatingPanel = true
panel.hidesOnDeactivate = false
panel.becomesKeyOnlyIfNeeded = false
panel.isOpaque = false
panel.backgroundColor = .clear
panel.contentView = FirstMouseHostingView(rootView: AlertRootView(session: session))
panel.makeKeyAndOrderFront(nil)                   // no NSApp.activate
```

**Why a non-activating panel.** Since macOS 14, a background app can't make itself the active app (cooperative activation), so an ordinary window plus `NSApp.activate` showed the alert but left the keyboard with whatever app the user was in. A `.nonactivatingPanel` becomes the key window without activating Join!: the user's app stays frontmost, the alert gets the keystrokes, and when it closes focus is simply back where it was.

**Keys.** An `NSEvent` local monitor, installed while an alert is presented and removed on dismiss, handles `Esc` (dismiss) and `Return` / keypad `Enter` (join, when a link exists) for events targeting one of the alert panels. Key auto-repeats, and keys pressed within 0.75 s of the alert appearing (`keyArmingDelay`, measured against each event's own timestamp), are swallowed so a keystroke the user was already typing or holding in another app can't dismiss the alert or join a call. After that, other keys pass through to the alert's views so Full Keyboard Access still works. SwiftUI `keyboardShortcut`s aren't used: they depend on the responder chain and silently did nothing in a borderless window. `FirstMouseHostingView` accepts the first click, so buttons on a secondary display's panel work without a focusing click. Only the first panel is made key; the others mirror the content.

**Backdrop.** `AlertBackdrop` (SwiftUI) stacks, bottom to top: an `NSVisualEffectView` (`material: .fullScreenUI`, `blendingMode: .behindWindow`) whose `appearance` is forced to `.darkAqua` / `.aqua` for the dark/light blur modes (left out for `.none`); the tint color at `tintStrength`; and a radial scrim behind the content (black at 32 % on dark backdrops, white at 50 % on light ones) that keeps text legible over busy wallpapers.

**Layout.** `AlertContentView` is shared by the alert and the Settings preview. A `TimelineView(.periodic(from:by: 1))` anchored on a whole second drives it, so the countdown steps evenly; the preview passes `mode: .preview(at:)` instead, a frozen clock that also draws the buttons with nothing to click or focus, and keeps no room above and below. Top to bottom, centered:

1. The calendar: a dot in the calendar's color and its name.
2. The countdown, colored by phase (below).
3. The title, 52 pt bold, up to two lines.
4. The time range (clock icon) and the location (pin), side by side, or stacked when they don't fit. The location is left out when it is only the join link again.
5. **Join**, when a link exists: a wide button with a video icon, "Join" before the start and "Join now" after, and a `↩` key hint.
6. The snooze row: a "Snooze" label, one button per snooze duration ("1 min", "5 min", "1 hr", worded like Settings), each duration once (`AlertCountdown.snoozeChoices`: when both snoozes in Settings read the same, the alert, the test full-screen alert and the Settings preview show one button, not two identical ones), and **At event start**, which snoozes until the meeting starts (VoiceOver: "Snooze until the event starts at 2:00 PM"). It is left out once the start has passed. The design's "At 2:00 PM" was renamed at the user's request.
7. **Dismiss**, with an `esc` key hint.

When several meetings share one plan, each gets its own calendar, countdown, title and details block (titles at 40 pt), above a single button group; the Join button names the meeting it joins ("Join Design Sync"). If the blocks don't fit the screen they scroll, with a fade at the edges, while the button group keeps its place, so Join, snooze and Dismiss always stay reachable. The hosting view has no sizing constraints, so the alert never grows past a small screen. The test full-screen alert adds the line "This is a test full-screen alert. Press Esc to close it." (`DemoEvent.fullScreenAlertNote`; "This is a demo full-screen alert." until 2026-10-19).

**Countdown.** `AlertCountdown` (JoinCore) turns `(start, end, now)` into a phase and its text. Colors come from `AlertPalette.countdownColor(for:)`: brighter on dark backdrops, deeper on light ones.

| Phase | When | Text | Color (dark / light backdrop) |
|---|---|---|---|
| before | before the start | "Starts in 2:59", "Starts in 1:05:00" (rounded up, so never "0:00" early) | amber `#FFB340` / `#A84B00` |
| starting | the first minute after the start | "Starting now" | orange `#FF9F0A` / `#A13A00` |
| started | after that | "Started 3 min ago", "Started 1 hr 5 min ago" | red `#FF6961` / `#C1121F` |
| ended | after the end | "Ended" | red |

It also builds the Join title, the snooze labels and their VoiceOver labels ("Snooze 5 minutes", "Snooze until 2:00 PM").

**Appearance and palette.** `AlertAppearance` (§3) stores only what the user chose; a `nil` color means Automatic. The views never pick colors themselves. They read `appearance.palette`, an `AlertPalette` of concrete colors:

- `surface`: an opaque stand-in for the blurred backdrop, `#26262B` for dark blur or `#ECECF0` for light, mixed with the tint at its strength.
- `text`: the custom color, or white / `#1D1D1F`, whichever contrasts more with the surface. That choice also sets `isDark`, which picks the countdown colors, the scrim and the automatic button fill.
- Join: the fill defaults to amber `#F5A524`, which Settings names Orange. The automatic label is white or near-black, whichever reads better on the fill.
- Snooze & Dismiss: the automatic fill is white at 16 % on a dark backdrop and black at 7 % on a light one. The automatic label is chosen by contrast, like Join's.
- Each button kind's fill opacity scales its fill, automatic or custom. Join's is limited to 40–100 % so the main action never disappears; Snooze & Dismiss goes from 0 to 100 %. Settings sets Join's to 100 % (only a look saved by an earlier build has less), and the Snooze & Dismiss buttons' through their swatches (22 %) or the opacity in their Other… well.
- `material`: the layer the blur adds over the desktop. Only the Settings preview draws it, because a window can't blur what is behind it inside itself.

`contrastWarnings` checks the event text, the Join label and the Snooze & Dismiss labels against their composited backgrounds. Each one under 4.5:1 (WCAG AA for body text) gets a warning with its ratio, rounded down so 4.46 reads "4.4:1", never "4.5:1", and the Colors row it shows directly under in Settings (`AlertContrastWarning.row`, §8). Every warning, the menu bar pill's too (§8), uses one template, `AlertContrastWarning.message(subject:ratio:advice:)`: "Event text may be hard to read (3.2:1)." and then advice that names the fix or what to try instead:

| Cause | Advice | Shown under |
|---|---|---|
| Event text on Other… | "Aim for 4.5:1, or choose Automatic." | Event text |
| Automatic event text on a tint | "Try a different tint strength." | Tint (below Strength) |
| The Join button, with a legacy label color | "Aim for 4.5:1, or set its Text to Automatic." | Join button |
| The Join button, otherwise | "Try another color." | Join button |
| Snooze and Dismiss, with a legacy label color | "Aim for 4.5:1, or set their Text to Automatic." | Snooze & Dismiss buttons |
| Snooze and Dismiss, on a swatch over a tint | "Try a different tint strength." | Snooze & Dismiss buttons |
| Snooze and Dismiss, otherwise | "Try another color." | Snooze & Dismiss buttons |

Automatic text on an untinted backdrop always reads, and every Join and Snooze & Dismiss swatch reads on every preset (tested), so no preset warns, and picking a button swatch on one doesn't either.

Presets (`AlertAppearancePreset`):

| Preset | Backdrop | Tint | Join | Snooze & Dismiss |
|---|---|---|---|---|
| Dark (default) | dark blur | none | amber, automatic label | automatic |
| Light | light blur | none | amber, automatic label | automatic |
| High contrast | dark blur | black at 70 % | `#FFD60A`, automatic label (near-black; black until 1.2.0) | white at 22 % |
| Midnight | dark blur | `#1E3A8A` at 45 % | `#2563EB`, automatic label | automatic |

`matchingPreset` compares appearances the way a person sees them (`isEquivalent`): the same backdrop and the same resolved palette (surface, text, Join label and fill, button label and fill) at 8 bits, alpha included. What's stored doesn't count, so a custom color equal to the automatic one, or a tint strength while there's no tint, changes nothing. Matching never rewrites what's stored: switching a pop-up to Other… starts from the color currently shown, so (Tint from None aside, §8) nothing changes until the user picks a new one, and normalizing that color to Automatic would snap the pop-up straight back. `style` (`AlertStyle`: a preset, or `.custom` while none matches) is the Style card Settings outlines, and `swatch` draws the Custom card's miniature like the presets'. The Snooze & Dismiss fill converts its opacity in both directions between Automatic and a color, so switching back and forth keeps the look. `isDefault`, which disables Restore Defaults, is stricter than matching Dark: there must also be no tint, and no stored event text color, label color or Snooze & Dismiss fill, so a legacy Text row, or Tint, Event text or Snooze & Dismiss left on Other…, keeps the button enabled even when the look matches Dark. Join's Other… stores its default Orange, which `isDefault` doesn't check (the alert shows Orange either way), so the Join button on Other… at Orange still counts as the default.

**Saved format.** The appearance is encoded as JSON with `"version": 3` since 1.2.0's swatches; missing keys fall back to the default. Version 2 has the same shape, and older builds still read version 3. Version 2 and JSON without a version (below) are migrated on load, in this order: a look that matches a preset, by today's definition or an earlier build's (High contrast with its black Join label), becomes that preset exactly, so no High contrast user gets a stray Text row; then an automatic button fill below 100 %, which Settings can no longer show now that Fill opacity is gone, becomes Other… at the same visible alpha: Join's default Orange at its opacity, and for Snooze & Dismiss the automatic white or black at exactly its opacity times the automatic 16 % or 7 %, unrounded, unlike Other…'s whole percents (`makeButtonFillCustom`), so no look of the user's own rounds into a preset's; custom label colors stay, each on its legacy Text row. Version 3 loads as saved. JSON without a version is the shape saved before the redesign, where every color was explicit (`textColor`, `backgroundTint` + `backgroundOpacity`, `button*` and `primary*` colors and opacities). An untouched old default becomes the new default. Anything customized keeps its exact colors: the background tint and opacity become `tint` and `tintStrength`, the primary button becomes Join (opacity clamped to 40–100 %), and the other buttons become Snooze & Dismiss. An old "No blur" survives, and only then does Settings offer it as a third Backdrop segment (`backdropChoices`).

## 7. Menu bar

`StatusItemController` owns an `NSStatusItem` and a `MenuBarPanelWindow`. SwiftUI's `MenuBarExtra` was used first and dropped: its window grows with its content but never shrinks, and it can't be closed programmatically. An `NSPopover` replaced it until the redesign, which called for a borderless panel with its own corners and material and no arrow. SwiftUI still requires one scene, so `JoinApp` declares a `MenuBarExtra` with `isInserted: .constant(false)`, which keeps SwiftUI's standard Edit menu (copy and paste in text fields) without adding UI.

**Status item.** `MenuBarPresenter.status(...)` (JoinCore) returns a `MenuBarStatus`: a kind, optional text and an accessibility label. Its inputs are the alertable meetings (only events whose Events choice is Show and alert, less those dismissed from the panel, §4), `now`, the `PauseState`, the `MenuBarDisplay` and the starting-soon window (`startingSoonPill.window`, 5 minutes by default). Precedence: paused > starting soon > in a meeting > within the hour > later, among the meetings `MenuBarPresenter.focus` keeps: a Maybe or unanswered meeting already in progress steps aside while a meeting you're attending (accepted, your own on a calendar you can edit, or organized by you) overlaps it and is on now or starts within the hour. So a long Maybe block in progress gives way to the call you accepted inside it ("Next in 47 min", not "4 h 17 min left") and comes back when nothing you've accepted is that close. Before it starts, a Maybe or unanswered meeting counts like any other, since its alert fires (a Maybe call inside an accepted meeting still gets its pill), and one that clashes with nothing you've accepted keeps its pill, ring and card. The user asked for this; declined events never get this far, since the calendar service drops them.

| Kind | When | Drawn as |
|---|---|---|
| idle | nothing upcoming in the 7-day window | `calendar` symbol alone |
| later | next meeting more than an hour away | `calendar` + a countdown later today ("Next in 11 h 40 min"), otherwise the day and time: "Tomorrow at 1:00 PM", "In 3 days at 9:10 AM" (calendar days). The user chose this over the design's "1:00 PM" / "Tomorrow 1:00 PM" / weekday. VoiceOver: "in 11 hours 40 minutes, at 1:00 PM", "tomorrow at 1:00 PM", "in 3 days, Thursday at 9:10 AM" |

- Durations are whole minutes rounded up, so "0 min" never shows before a start. Time left beyond an hour reads "2 h 15 min".
- Settings › General › Menu bar › **Shows** picks one of three (`MenuBarDisplay`, stored as `menuBarShowsNextEvent` and `menuBarShowsEventTitles`): **Icon only**, **Time until next event** (the default), or **Title and time until next event**. Without a title a countdown starts with "Next" ("Next in 42 min"); with one, the title takes its place, truncated to 24 characters: "Product Planning · in 4 min".
- With **Icon only**, the item has no text but keeps its state icon (pill, ring, bell).
- Plain states use template images, so the menu bar tints them. The pill is drawn in full color, and redrawn when the system colors change. Text uses a monospaced-digit font, and countdowns past an hour always show two-digit minutes ("11 h 05 min", "2 h 00 min left", `MenuBarPresenter.steadyDuration`), so the item keeps its width as the minutes tick instead of nudging every other menu bar item each hour. The panel keeps the shorter "2 h".
- The button re-renders through observation tracking whenever `AppModel.menuBarStatus` or the pill's settings (`Preferences.startingSoonPill`) change, and when the system colors change. `AppModel.now` ticks on every :00 and :30 of the clock, so countdowns stay in step with meetings, which start on whole minutes.
- VoiceOver reads full words: "Join!: Product Planning starts in 4 minutes", or "Join!: alerts paused" ("…full-screen alerts paused" until 1.3.0).

**Panel window.** `MenuBarPanelWindow` is a borderless, non-activating `NSPanel` at `.statusBar` level, 368 pt wide, on all Spaces. Like the alert, it takes Esc and Return without pulling the user's app out of the foreground. Its background is the system menus' material with a frost over it (below). On macOS 26 and later it's an `NSGlassEffectView` (Liquid Glass, 14 pt corners), behind an availability check since the app still runs on macOS 14, and set up through its typed `style` (pinned to `.regular`, which adapts the backdrop's luminance; clear doesn't), `cornerRadius` and `contentView`. Before macOS 26 it's an `NSVisualEffectView` with the `.menu` material and a rounded mask image, which shapes both the blur and the window shadow. The glass sits in a layer-backed view clipped to the same continuous rounded rectangle: unclipped, the glass gave the window a square shadow, a dark outline with darkened corners around the rounded panel. **Frost.** Bare glass let the backdrop's brightness through: over a white window, dark-mode glass settles at mid-gray, where even pure white text only reaches about 4.3:1, and the old grays (tuned for a solid panel) measured 1–2:1 on the user's screenshots. So `MenuBarPanelView` lays a frost between the glass and the content, `#1E1E20` (dark) or `#FAFAFC` (light) at 50%: text sits on a steadier surface, while half of the glass (the wallpaper's color, its depth and edge) still shows. The canvas recommended 70%, which kept more contrast margin; the user chose 50% on screen. It's 88% with Increase Contrast, opaque with Reduce Transparency, and 40% over the pre-macOS 26 menu blur, which is already thick. The design canvas compared this with a glass rim around a solid sheet, tiles per section, and a glass header over a content floor; the user chose the frost. The `panelFrost` hook (§12) tries other opacities on the real panel. The SwiftUI view sits in an `NSHostingView` that accepts the first click.

**Sizing.** `MenuBarPanelView` measures its header and its body with `GeometryReader` preferences and reports the sum through `MenuBarPanelContext`. The controller hangs the panel 6 pt below the status item with the top edge fixed, and sets the height to that natural height, capped at 640 pt and at the room left above the bottom of the screen (minus an 8 pt margin). The x position follows the item and is nudged to stay on screen. It's set when the panel opens; while it's open only the height follows the content, because the item changes width with its text (pausing shrinks it to a bell) and the panel would jump sideways with it. The resize runs on the next run-loop turn, because resizing the window from inside a SwiftUI layout pass re-enters layout. When the content is taller than the panel, the body scrolls and a 32 pt fade at the bottom shows there is more. It fades into the frost and only down to 40%, so the last row stays legible, and its strength follows how much is still hidden, so it is gone at the end of the list. The Today | 7 Days switch changes the height too: the list snaps to its new length and the window follows in one step; only the switch's thumb slides.

**Closing and keys.** The panel closes on Esc, ⌘W, a second click on the item, a click anywhere else (global and local event monitors), the app resigning active, another window becoming key (except while one of the panel's own menus is open), a Space change and a display change. It also closes before Join, Directions, Settings or Open System Settings open anything, and before any alert appears. ⌘, opens Settings and ⌘Q quits. ⌘1 and ⌘2 pick Today or 7 Days, matched by key (the number row's and the keypad's) so they also work on layouts like AZERTY; the thumb slides as for a click. When that half can't be picked (the switch is hidden, or nothing is left today) the panel beeps. Return runs the hero card's Join or Directions button (never Dismiss) when the hero is Starting soon or Now; with neither, it does nothing.

**Panel content.** `PanelPresenter.content(meetings:alertable:dismissed:now:startingSoonWindow:)` (JoinCore) returns one hero card and a list of sections. It lists exactly the meetings it's given, `MeetingStore.meetings` (the visible ones, §4); before 1.2.0 it also took `showsOutOfOffice:` to drop out-of-office rows, which the Exclude choice now does upstream. `dismissed` is `MeetingStore.dismissals`: the Show and alert meetings among the dismissed events, by `Meeting.ID`, each with how it was dismissed, on its own (`.thisEvent`) or with its series (`.allFutureEvents`) (`MeetingFilter.dismissals`). One map rather than two sets of ids, so an occurrence can't be dismissed with its series without being dismissed. They're marked in the lists (Dismissing, below). The views draw them with `PanelColors`, resolved from `PanelPalette` (JoinCore) for the drawing appearance and Increase Contrast: five inks (primary, strong, secondary, tertiary, warning) instead of ten grays, and fills as fixed opacities of black or white that match the system fills. The inks stay fixed sRGB, not vibrant: AppKit only gives vibrancy to SwiftUI's hierarchical styles, which can't be held to a contrast, and even vibrant white can't reach 4.5:1 on bare glass over a white window. `PanelPaletteTests` checks every ink at 4.5:1 on the frost over the lightest dark glass and the darkest light glass measured on the user's screenshots (`#7A7A7A` over a white window, `#8D8E8F` over a dark one; a brighter or darker backdrop can dip below that at 50%), on the hero card and the out-of-office stripes, and, for every system accent, on the starting-soon card and on the prominent button at rest and under the pointer. The prominent button is solved per accent (`PanelPalette.accentButton`): the accent darkened 15% (20% in dark mode), since white on the plain default blue is under 4.5:1; the better of white and near-black as the label (near-black on yellow, orange, green); the fill stepped further from the label until it reads at 4.5:1; and a hover fill that moves further the same way, so pointing can only raise the contrast. The starting-soon card is the regular card with the accent tint over it: 12% in light mode, and in dark mode up to 10%, less for bright accents (down to none for yellow), until its text keeps 4.5:1 (the accent border still marks it). "Starts in 4 min" is the accent stepped toward white or black until it reads at 4.6:1 on that card. Cards (hero, nothing-today, paused bar, update bar, permission prompt) are white at 55% in light mode, away from the dark text, and white at 6% in dark mode, with a separator edge. With Increase Contrast the inks go further toward black or white, the separators get stronger, and the filled buttons, the active header button and the switch get a 3:1 edge (the switch's thumb edge is drawn 1 pt wide).

    - **What each choice does** (`DismissedEvents`): **Dismiss This Event** dismisses this occurrence (nothing changes when All Future Events already covers it, unless it had been restored on its own). **Dismiss All Future Events** dismisses it and every later occurrence of the series, those beyond the 7-day window and those not in the calendar yet included, until restored: a series rule from this occurrence's start, with no end. Occurrences of the series dismissed or restored on their own from there on are folded into it; chosen on an occurrence earlier than a rule's start, it moves the rule's start back. **Restore This Event** brings back this occurrence only; inside a rule it's an exception, and the rest of the series stays dismissed. **Restore All Future Events** brings back this occurrence and every later one, however they were dismissed: the rule stops at this occurrence (or goes, if it started here or later), and earlier occurrences that are still listed and dismissed stay dismissed. An occurrence counts as later when it starts at or after the chosen one's start, so one edited on its own to an earlier time counts by its new start.

The panel stays open. `MeetingStore.alertableMeetings` reads the dismissed events, so both alert coordinators (§5), the menu bar item and the card follow that one write. One function decides whether a meeting is dismissed, `DismissedEvents.isDismissed(_:)`: an occurrence dismissed on its own (`occurrences`, by `Meeting.id`), or one a rule of its series covers (`seriesRules`, by `Meeting.seriesID`: from a start, with no end or up to a later start) that wasn't restored on its own (`exceptions`, by `Meeting.id`). `MeetingFilter.alertable` and `dismissals` ask it, so the store, the presenter's `dismissed` map and everything after them follow series rules too. A series usually has one rule; a second appears when All Future Events is chosen past where Restore All Future Events stopped the first, so the occurrences still listed before that stay dismissed. Entries go once their events are over: `MeetingStore.refresh()` prunes against each fetch (`DismissedEvents.pruned(at:meetings:)`), and only writes when something changed. An occurrence or exception whose event is in the fetch takes that event's end as it is now, so an event extended after it was dismissed stays dismissed until its new end; one whose event is missing from it (moved, deleted, or on a calendar that was unchecked) is kept until its stored end. A rule with no end never expires, since it covers occurrences not in the calendar yet; a rule stopped by Restore All Future Events goes once that start has passed and none of its occurrences in the fetch is still running, and exceptions go with their rule. The entries survive a relaunch, and nothing in Settings resets them; series dismissals are managed from the list only (the user's choice), with no list of them in Settings.

The calendar-permission prompt keeps standard system buttons, which don't change the cursor.
- **Overlaps.** A meeting that starts while an earlier one is still running is flagged with the latest-ending of those. ## 8. Settings window

Dependent settings (Repeat until it's closed, the Custom time rows, the tint's Strength) are drawn as children of the row above: indented 30 pt, with their hairline starting at the indent and an elbow line running from under the parent's label to their own (`SettingsRow(indented:)`). They only show while their parent is on, and are hidden, never dimmed, while it's off: Repeat only with a sound, a Custom time row only while its pop-up is on Custom…, Strength only while there's a tint. The user asked for this for every nested option (2026-10-07). Hiding Repeat or Strength keeps its stored value, so it comes back as it was. A color well likewise only shows while its pop-up is on Other…, and a legacy Text row only while a label color saved by an earlier build is stored. Rows that sit beside a setting rather than under it are another matter: with **Alert me** on **Never**, **Show on**, **Sound**, Repeat and **Close automatically** stay in view, dimmed and disabled, and so does **Play sound** with **Notify me** on Never (below). A row appearing or disappearing resizes the window like any other height change (Sizing, below).

`SettingsWindowController` owns a plain AppKit window whose content view controller is an `NSTabViewController` with `tabStyle = .toolbar`: one toolbar item per pane, **General** (`gearshape`), **Alerts** (`bell`, the symbol of the panel's Pause alerts), **Calendars** (`calendar`) and **Appearance** (`paintpalette`), in that order (`SettingsPane`, in JoinCore: `general`, `alerts`, `calendars`, `appearance`, with each pane's label and symbol). Alerts is second since 2026-10-19, when the user asked: "Put the 'Alerts' tab in the second position." It was third, after Calendars, before; the raw values, and so the `openSettings` hook, didn't change. Each pane has one subject, since the user's regroup for 1.2.0 (2026-10-08): General the app and the menu bar, Calendars the calendars, Alerts when each kind of alert comes and how it's snoozed and closed, Appearance how the full-screen alert looks. Alerts was **Full-Screen Alert** (`fullScreenAlert`) until 1.3.0, when notifications joined it. The labels are in title style, like other macOS toolbar items. SwiftUI's `Settings` scene can't be opened dependably from a menu-bar-only app. The window uses `toolbarStyle = .preference`, takes the selected pane's title, and can be closed but not resized. Panes switch instantly, as the user asked for 1.2.0: `transitionOptions` is empty, so there's no crossfade. It opens from the gear menu, ⌘, in the panel, reopening the app (`applicationShouldHandleReopen`, except just after a response to a notification, §5), System Settings › Notifications › Join!'s link back, which opens Alerts, or the `openSettings` script hook (§12), which can also pick the pane.

**In front.** Every way in goes through `SettingsWindowController.show`, which puts the window in front of every app's windows, whether it's new or already open behind them, then asks for Join! to become the active app, so the window has the keyboard. Before 1.3.0 Settings sometimes opened behind the app in use (the user's report, 2026-10-15). Since macOS 14 activation is cooperative (§15): `NSApp.activate()` is a request the system may turn down, and `activate(ignoringOtherApps:)` is deprecated, its flag ignored. Join! is seldom the active app when Settings opens, since the panel takes the keyboard without activating it. `show` asked for activation first, while Join! had no window on screen (the panel had just closed), then called `makeKeyAndOrderFront` alone, which from an app that isn't active puts the window in front of the app's own windows only, below the active app's. So whenever the request was turned down, Settings stayed behind. A scratch app on macOS 27 asking without user input showed both halves: the request was turned down, `makeKeyAndOrderFront` left its window second among the normal windows, behind the active app's, and `orderFrontRegardless` put it first. Now:

- `makeKeyAndOrderFront` then `orderFrontRegardless`: the window is in front whatever becomes of the request.
- `NSApp.activate()` on the next turn of the main queue: the window server only lists a window ordered in once the current turn ends, and it may turn down a request from an app with no window on screen; a menu that chose Settings has finished closing by then too.

After a click or a key in Join! (the gear menu, ⌘, in the panel) or a reopen from Finder, the request is granted, Join! is the active app and Settings is key. When it isn't, as for the `openSettings` hook posted while the user is in another app, Settings still shows in front, inactive, and the first click on it activates Join!. Nothing deprecated is called, and no window level is raised: Settings stays an ordinary window that other apps' windows can cover again once the user moves on.

**Sizing.** Each pane is a SwiftUI view in an `NSHostingView` with `sizingOptions = []`, wrapped in `SettingsPaneScroll`, which reports the content's natural height through a preference. The window keeps a 720 pt content width and takes the selected pane's height, in one step when switching panes, never animated (1.2.0 dropped the animated resize with the crossfade). A height change from within a pane (a style adding the tint's Strength row, or picking a sound bringing back Repeat, say) resizes it without animation on the next run-loop turn: SwiftUI reports the new height from inside its layout pass, and resizing the window there left the window's content view out of step with its frame by the height change, so the pane slid under the toolbar or below a gap. It keeps its top edge in place and stays on screen. It only scrolls when the screen is too short for the pane.

**Focus.** Opening the window, switching panes and closing the window all clear the first responder. That stops AppKit from focusing the first text field on open, and commits a half-typed value the same way as when the field loses focus.

1. **Pane:** a leading `VStack`, `sectionSpacing` (22) between blocks, padded 20 at the top and sides and 24 at the bottom. No pane sets its own spacing. Blocks are sections; Calendars also has an intro line at the top and a footer.
2. **Section** (`SettingsSection`): a `.body` semibold heading, primary, 2 pt in, on one line with tail truncation, with the header trait; 8 to the box; 6 from the box to the line under it.
3. **Headings:** every box has one, with two exceptions: (a) a pane's first block, at the top padding, whose content names itself (General's Open at login box, Appearance's preview box), built with `SettingsSection(title: nil)`; (b) a pane-wide state that stands in for the sections (Calendars' permission prompt and "No calendars yet").
4. **Box** (`SettingsBox`): 12 pt horizontal inset, 10 pt continuous corners, `SettingsPalette.box` with a 1 pt `boxBorder`, no vertical padding: rows set the height. 5. **Row** (`SettingsRow`): label, spacer, control at the trailing edge. 6. **Control line:** every right-aligned item ends 12 pt in from the box's edge, x = 688 in the pane (1375 px in a 2x screenshot): inside a box through its inset, under it through the line's trailing padding. Nothing sits on the box's outer edge.
7. **Controls:** pop-ups `.labelsHidden().fixedSize()` at regular size, never a fixed width; switches `.switch` at small size; segmented controls labels hidden and fitted, at regular size; sliders a fixed 220 with their value right after; buttons regular bordered push buttons, text only, Sound's play button being the one icon button. No link-style buttons, and no font or control-size overrides on controls.
8. **Helpers:** a control's helper (the play button, the menu bar's preview, a color well) sits before it, 8 away, so the control's right edge stays on the line whether the helper shows or not.
9. **Nesting:** a dependent row is indented 30 with the elbow, its hairline starting at the indent, and hidden, not dimmed, while its parent is off; a row that another setting turns off stays in view with the disabled tone and a disabled control.
10. **Line under a box** (`SettingsNoteLine`): `HStack(alignment: .firstTextBaseline, spacing: 16)`; at the left the footnote and the warning, 4 apart, 2 in, filling the width; at the right the buttons, 8 apart, with 12 trailing padding; drawn only when there's something to show. **Persistence.** `Preferences` is an `@Observable` class whose stored properties read/write `UserDefaults` (theme encoded as JSON `Data`). No `@AppStorage` scattered across views; one owner. Values stored by older builds are migrated on load:

- Lead times with seconds are rounded to whole minutes. Every write is rounded too.
- The old `showOnAllScreens` Bool becomes `alertScreens`: true → all screens, false → main screen. Writing the new key removes the old one.
- `alertScreens` gains `secondary` in 1.2.0; `all`, `main` and `pointer` keep their stored values. Builds before 1.2.0 don't know `secondary` and show the alert on all screens.
- `menuBarShowsEventTitles` is new and starts off. Builds before the redesign always showed the title.
- `checksForUpdates` is new in 1.1.0 and starts on, so a copy updated by hand from 1.0.0 checks from its first launch.
- `eventsWithoutParticipants` is new in 1.2.0. Until it's set, it comes from 1.1's switch, `showsEventsWithoutParticipants`: on or absent → Show and alert, off → Exclude.
- `outOfOfficeEvents` is new in 1.2.0. Until it's set, it comes from the two out-of-office switches of 1.0 and 1.1. `alertForOutOfOffice` on → Show and alert, whatever `showOutOfOfficeInList` says, so those alerts keep working. With it off, `showOutOfOfficeInList` on or absent → Show in the list only, off → Exclude. When `alertForOutOfOffice` is absent, the inverse of the older `skipOutOfOffice` stands in for it, and with neither it counts as off.
- Setting either choice removes the old keys it was read from, as `alertScreens` does. A stored value that isn't one of the three choices is ignored, so the old keys or the default apply.
- `fullScreenAlertsEnabled` is new in 1.2.0 and starts on. A stored lead time of 2 or 10 minutes is kept and shows as Custom.
- The appearance JSON migrates as described in §6.
- `customAppearance` is new in 1.2.0. On the first load without it, a stored appearance that matches no preset becomes the Custom card's look and is saved as such, so a look of the user's own opens on Custom. A stored one that matches a preset is ignored.
- `dismissedEvents` is new in 1.2.0 and starts empty. It isn't a setting: Restore Defaults and the other resets leave it alone (§7). 1.3.0 saves it in a new shape, `{"occurrences": {…}, "seriesRules": {…}, "exceptions": {…}}`, for repeating events (§7). 1.2.0's plain object of occurrence id → end still reads, each entry as an occurrence dismissed on its own; its start and series are filled in once its event is fetched. 1.2.0 can't read the new shape, so going back to it loads no dismissals, as for any unreadable value.
- `notificationsEnabled` (false: **Notify me** is Never), `notificationLeadTime` (300 s, in whole minutes like `leadTime`) and `notificationPlaysSound` (true) are new in 1.3.0 and read as those defaults while absent, so an upgrade from 1.2.x keeps exactly its behaviour: nothing is sent, and macOS isn't asked, until the user picks a time. Reading them writes nothing. `notificationStates`, the notification's per-meeting states that `NotificationCoordinator` keeps beside `alertStates` (§5), is new too and starts empty. No stored value changes meaning: `leadTime`, `fullScreenAlertsEnabled`, `alertScreens`, `soundName`, `soundRepeats`, `autoCloseEnabled` and `autoCloseAfter` stay the full-screen alert's (**Close automatically** only moved on screen), while `snoozeDurations`, `pauseState` and `dismissedEvents` now apply to both kinds. The `openSettings` hook still takes `fullScreenAlert`, the Alerts pane's name before 1.3.0 (§12). Going back to 1.2.x ignores the new keys, so notifications simply stop; any already delivered stay in Notification Center until closed, since 1.2.x doesn't know to remove them, and the permission stays in System Settings, keyed to the bundle id.

## 9a. Out-of-office events

EventKit doesn't expose Google's "out of office" event type, but Google titles those events predictably in the account's language ("Out of office", "Fuera de la oficina", …). `OutOfOfficeDetector` matches the title against a keyword list (short tokens like "OOO" and "PTO" must stand alone), edited under **Out-of-office keywords** in Settings › General › Events. What happens to matching events is the **Out-of-office events** choice in the same section (§4). It's **Show in the list only** by default: they never alert and don't drive the menu bar item or the panel's hero card, and they appear in the panel's lists as striped, muted rows with no button. **Show and alert** lets them alert and drive the menu bar like any other event, and be dismissed from the panel (§7), still striped in the lists; **Exclude** leaves them out everywhere. Whatever the choice, they never count as overlaps.

An out-of-office block nobody else is on is also an event with no participants, so it gets whichever of the two choices shows less: with **Events with no participants** on Exclude, it's left out whatever the out-of-office choice says. One with participants follows the out-of-office choice alone.

## 9. Meeting link detection

```swift
enum MeetingLinkDetector {
    static func joinURL(in meeting: Meeting) -> URL?
}
```

Walks an ordered provider table; for each provider it checks `url`, `location`, then `notes`. A match from an earlier provider wins regardless of field:

| Provider | Pattern |
|---|---|
| Google Meet | `https://meet.google.com/[a-z]{3}-[a-z]{4}-[a-z]{3}` |
| Zoom | `https://[\w.-]*zoom\.us/(j|my|s)/[^\s>"]+` |
| Microsoft Teams | `https://teams\.microsoft\.com/l/meetup-join/[^\s>"]+` |
| Webex | `https://[\w.-]+\.webex\.com/[^\s>"]+` |
| Generic fallback | any `https://` URL in `location` only. The `url` field is excluded on purpose: calendar backends often put the event's own web page there, which would give every event a bogus Join button. |

Adding a provider is one table row plus a test case. Each pattern is compiled once, beside its provider; a pattern that doesn't compile is a programmer mistake, so it stops the app (`preconditionFailure`, which the tests would hit first) rather than leaving that provider's links silently undetected. Opening uses `NSWorkspace.shared.open(url)` (system default browser or handler). A meeting with no link but a physical location gets a Directions button in the panel instead (§7).

## 10. Edge cases handled

| Case | Behaviour |
|---|---|
| Mac asleep through the fire time | On wake: refetch, `nextPlan` sees `fireAt < now < end` → fires immediately. |
| App launched 1 min before a meeting | Same path: fires on first plan. |
| Meeting created less than `leadTime` before start | `EKEventStoreChanged` → re-plan → fires now. |
| Meeting cancelled while alert showing | Store no longer contains it → coordinator closes the alert. |
| Meeting moved | New `id`, old state discarded, new occurrence scheduled. |
| An event only you are on (focus time, a reminder, a hold) | Shows and alerts like any other by default. On **Show in the list only** it stays in the panel's lists only; on **Exclude** it's left out of the panel, the menu bar and alerts. Choosing Show and alert again brings it back at once. |
| An event's Events choice changes away from Show and alert while its alert is on screen | It leaves `alertableMeetings`, so the alert closes, as for a cancelled meeting. |
| An event dismissed from the panel while its alert is on screen | The same: the alert drops it, closing if it was the only meeting. Restore doesn't show that alert again. |
| A dismissed event is extended or moved | Extended, it stays dismissed until its new end. Moved to another start, it has a new `id`, so it's no longer dismissed; the old entry goes at its stored end. |
| A repeating event dismissed with All Future Events gets another occurrence (the 7-day window moves on, the series is extended) | Dismissed: the rule covers every occurrence from its start on, fetched or not, until Restore All Future Events. |
| One occurrence of such a series is edited on its own | It's still in the series (`isDetached`), so the rule covers it by its new start. Moved, it has a new `id`, so a Restore This Event made for its old start no longer applies. |
| A repeating event stops repeating | Its occurrences no longer have a series, so a rule doesn't cover them; an occurrence dismissed on its own stays dismissed. |
| An out-of-office block nobody else is on | It's both kinds, so the choice that shows less applies (§9a). |
| **Alert me** set to **Never** while an alert is on screen | The alert stays until it's closed; pending and snoozed alerts don't fire. The menu bar and the panel carry on. |
| A time picked again after **Never** | Re-plan with that time; a meeting that started less than 5 minutes ago alerts right away, as when a pause ends. |
| Two meetings at the same time | One alert listing both. |
| Next meeting starts while you're in one | Within the starting-soon window (5 minutes by default) it takes over the menu bar item (pill) and the panel's hero card; the ongoing one moves to "Now". |
| Two meetings overlap | The later one is flagged in the panel ("Overlaps …"); both alert normally. |
| Meeting runs past midnight | Time range reads "11:30 PM – 12:30 AM"; longer than a day, "Mon 9:00 AM – Wed 5:00 PM". `DateIntervalFormatter` alone prints full dates as soon as a range crosses midnight. |
| Lead time changed in Settings | Re-plan; a meeting already `.dismissed` stays dismissed. |
| **Notify me**'s time changed | Re-plan; a meeting already notified isn't notified again (`NotificationSchedule.sentState`). |
| Sound set to None while **Repeat until it's closed** is on | The Repeat row hides and its stored value is kept; with no sound there's nothing to repeat. Picking a sound again shows the switch, still on. |
| Paused until tomorrow, then the app relaunches | The pause is read back from UserDefaults; an expired one is dropped. |
| A timed pause runs out | The next heartbeat (≤ 30 s) clears it; a meeting about to start alerts right away, with each kind that has a time. |
| User in a full-screen app on another Space | `.canJoinAllSpaces` + `.fullScreenAuxiliary` + `.screenSaver` level shows over it. |
| Display plugged/unplugged during alert | Windows rebuilt from current `NSScreen.screens` (for "Screen with the pointer", the screen the pointer is on at that moment; for "Secondary screen only", the main screen once no other is left). |
| More meetings than fit in the panel | The panel stops at 640 pt or the bottom of the screen and scrolls, with a fade at the bottom. |
| Focus / Do Not Disturb on, full-screen alert | Ignored by design; the whole point is to interrupt. Documented. |
| Focus / Do Not Disturb on, notification | macOS holds it quietly in Notification Center unless the user allows Join! in that Focus: Join! posts at the Active level, never Time Sensitive (§5), and can't detect a Focus. The Notification box's footnote says so, and the full-screen alert still comes if it has a time. |
| Screen mirrored or shared (presenting in a call; some docks count as sharing) | By default macOS holds every notification meanwhile (System Settings › Notifications, when mirroring or sharing the display), so someone with notifications only can miss the next meeting while presenting. Join! can't tell. The footnote names screen sharing, and the full-screen alert is unaffected: a trade accepted with Direction A (2026-10-16). |
| Notifications denied, at macOS's prompt or later in System Settings | **Notify me** keeps its time. The status line reads "Allow notifications for Join! in System Settings › Notifications." in orange, with **Open System Settings**, and Test Notification is disabled ("Allow notifications for Join! in System Settings first."). Join! doesn't ask again: macOS prompts only once. A notification due meanwhile is marked sent and its post fails (logged), so allowing them later brings only the ones still to come. |
| macOS's prompt left unanswered | Still undecided: the secondary line "Allow notifications from Join! when macOS asks, or in System Settings › Notifications." Nothing is sent for the first minute after asking; then the heartbeat sends what's due, and nothing reaches the screen until notifications are allowed. The next time Notify me leaves Never, or Test Notification is clicked, Join! asks again. |
| Allowed, but set in System Settings never to show on screen (only to Notification Center) | The orange line "Show Join!'s notifications on screen in System Settings › Notifications." There's no line for banners that close on their own, macOS's default: the footnote covers how long a notification stays. |
| **Play sound** on, but sound off for Join! in System Settings | The secondary line "Turn on sound for Join! in System Settings › Notifications."; the notification comes silently. |
| A meeting's notification and full-screen alert due at once (the same time for both, or both caught up after a pause, sleep or a late launch) | The full-screen alert goes up first and the notification comes silently, so the two sounds never overlap. Whether the banner shows above the alert's `.screenSaver` window is still to be checked on a real build (§12). |
| A notification due while Settings is in front | It shows as usual (`willPresent`). |
| Clicking a notification | Nothing happens and nothing opens: the reopen event macOS may send with the click is ignored for a second (§5). The meeting's full-screen alert still comes at its time. A click on one left from before Join! quit launches Join!, as macOS does for any app, and nothing more happens (below). |
| **Join** on a notification while the meeting's full-screen alert is on screen | The meeting leaves the alert, which closes if it was the only one; neither kind comes back. |
| **Snooze** on a notification, the full-screen alert still to come | The notification comes back after the snooze, replacing itself; the full-screen alert comes at its own time. |
| A meeting with a delivered notification is dismissed from the panel, cancelled, moved, set to Show in the list only or Exclude, or ends | The notification is withdrawn: at once, or by the next heartbeat (≤ 30 s) once the meeting ends. |
| **Notify me** set to **Never**, or alerts paused, with a notification delivered | It stays until it's closed or its meeting goes; nothing more is sent until a time is picked or the pause ends. |
| Join! quit with notifications delivered | They stay in Notification Center. The next launch withdraws those whose meeting has gone or ended, once the calendar has been read. A click on one while Join! isn't running launches it, whether on an action or on the notification itself. The responder, set before launch finishes, handles an action from what the notification carries; a click on the notification itself does nothing more. |
| Upgrade from 1.2.x | **Notify me** reads Never: no prompt and no notification until a time is picked (§8). |
| A calendar's own event alerts are on too | A meeting may notify twice, once from the calendar's own alert and once from Join!. Join! can't tell; the README says so. |
| Calendar permission revoked at runtime | `EKEventStoreChanged` refetch returns nothing; menu bar panel shows the permission prompt. |
| Timezone change while running | Heartbeat re-plans with fresh `Date()`; events are stored as absolute instants. |

- **Fixture calendars.** The `JOIN_FIXTURE` environment variable swaps EventKit for `FixtureCalendarService`, so the menu bar and Settings can be checked in a known state:

  `JOIN_SETTINGS_MAX_HEIGHT=<points>` (fixture runs only) caps the Settings window's content height, to check the scrolling layout of a short screen on a tall one.

  `JOIN_FIXTURE_UPDATE` (fixture runs only) picks what the update check finds, through `FixtureReleaseFeed`: `current` (the default) the running version, `available` a release one minor version above it with a Join.zip, `failed` an error. None of them touches the network, and with them Install shows "Not available in fixture mode." `ready` is for seeing the ready state without the network: its first check finds what `available` finds and each later check (Check Now) one patch version more, so a newer release replacing a ready one can be seen too, and Install goes through `FixtureUpdateInstaller`: about three seconds of pretend download, a second of "Verifying…", then the ready bar with **Install and Relaunch**, which relaunches the fixture as it is, through the real relaunch helper, replacing nothing (the relaunched fixture offers the update again). It touches neither the network nor the disk. `live` uses `GitHubReleaseFeed` and lets Install download and verify a real release and Install and Relaunch install it, replacing the bundle the fixture runs from; it's only for testing updates end to end. Except with `live`, a fixture run keeps the update check's results (when it last checked, the offered and the unsupported versions) in memory only, never in the fixture defaults, so every fixture launch checks once, straight away, and each value shows its result whatever an earlier run found. When Join! can't replace itself, a fixture run reveals the new copy in `$TMPDIR/JoinUpdate/`, never in ~/Downloads, and a fixture relaunched after an install keeps `JOIN_FIXTURE` and `JOIN_FIXTURE_UPDATE`.

  ```sh
  open --env JOIN_FIXTURE=busy --env JOIN_FIXTURE_UPDATE=available build/Join.app
  ```

  `JOIN_FIXTURE_NOTIFICATIONS` (fixture runs only) sets the notification permission the Alerts pane sees. A fixture run has the app's bundle id, and with it the real app's notification permission, list and System Settings entry, so it never touches the real notification center: no prompt, no posting, no responder, no withdrawals. `FixtureNotificationCenter` stands in, and logs what it would do (category `fixture`). The values (`NotificationPermission.fixture`): `notDetermined` (the default, and what anything else reads as), `denied`, `hidden` (allowed, never on screen), `soundOff` (allowed, macOS's sound for Join! off) and `authorized`. Test Notification is disabled ("Not available in fixture mode."), and the run never plans or sends a notification.   ```sh


  `JOIN_FIXTURE_REGULAR=1` (fixture runs only) gives Join! a Dock icon and a menu bar of its own, so UI automation tools that only see regular apps can click through Settings. Some bugs only show up with real clicks, not with the script hooks below.

Unlike a real calendar's, a fixture series' occurrences keep ids of their own (`planning`, `planning2`), so the hooks below can name each one; only `seriesID` ties them together. Meeting ids are occurrence ids (`workshop@<start>`), like the real calendar's, so a dismissal (§7) doesn't carry into later runs: today's events move with each launch, and the ones on the following days (`workshop2`, `planning2`, …) keep their ids only through relaunches on the same day, so a dismissed one stays dismissed until it ends, like a real event. A series dismissal (**Dismiss All Future Events**, or the `dismissFutureEvents` hook) is cleared when the next fixture run starts: the series ids are the same in every launch and the rule has no end, so it would dismiss every later run's occurrences. `AppModel` drops the series rules, and the exceptions inside them, at launch in a fixture run, and keeps the occurrences dismissed one by one (`DismissedEvents.withoutSeriesRules`). Only these six names turn fixture mode on; any other value is logged and ignored, so a typo launches the real app. A fixture run uses its own defaults domain (`com.poliuk.join.fixture`), so it can't change real settings, never starts the alert scheduler, so it can't put an alert on screen by itself, never plans or sends a notification and never touches macOS's notification center (`JOIN_FIXTURE_NOTIFICATIONS`, above), leaves the login item alone, and doesn't go online for updates unless `JOIN_FIXTURE_UPDATE=live`. ## 13. Build, CI, distribution

- **Toolchain:** `swift-tools-version:6.2`, the first with `defaultIsolation`, so Swift 6.2 or later: Xcode 26 or later, or their Command Line Tools. CI builds with Swift 6.3 (Xcode 26.6) and the author's Mac with Swift 6.4 (the Command Line Tools for Xcode 27), so the code uses nothing newer than 6.3. Every target, the tests included, is in the Swift 6 mode.
- **SDK:** the Command Line Tools for Xcode 27 default to the macOS 27 SDK, where SwiftUI's `@State` is a macro expanded by a plugin (`SwiftUIMacros`) that ships only with Xcode, so the app doesn't build against it with the Command Line Tools alone. They also install the macOS 26.5 SDK, which builds it. `scripts/select-sdk.sh`, sourced by `scripts/build-app.sh` and by `make build` and `make test`, exports `SDKROOT` for SwiftPM: the caller's `SDKROOT` when it's set; otherwise the default SDK, unless the developer directory has no SwiftUI macro plugin and that SDK declares `@State` as one of its macros, and then the newest `MacOSX26*.sdk` beside it. So it works the same with Xcode selected (its default SDK) and with only the Command Line Tools. Plain `swift build` and `swift test` on the Command Line Tools need `SDKROOT=/Library/Developer/CommandLineTools/SDKs/MacOSX26.5.sdk`. `make test` also names the toolchain's Swift Testing plugin folder, for the Swift Build bug §12 describes. The SDK only decides what the app compiles against; it still runs on macOS 14.
- **Design:** `Info.plist` sets `UIDesignRequiresCompatibility`, so macOS 26 and later draw the app's standard controls (Settings' toolbar, pop-ups, buttons) in the design it was made for, as 1.2.0 looked. Built with a macOS 26 SDK for 1.3.0, the app had switched to the new design by itself: the Settings toolbar's selected tab became a white glass box tinted with the accent color, over our gray panes and white cards, and the user said it didn't look right (2026-10-16). The panel's glass is `NSGlassEffectView`, used directly, so it's unaffected. Apple calls the key temporary; when a macOS release stops honouring it, Settings needs a design pass for the new look.
- **Build:** `make app` runs `scripts/build-app.sh`: it picks the SDK as above, runs `swift build -c release` once per architecture in `ARCHS` (this Mac's by default; releases pass `arm64 x86_64`) and copies each architecture's binary out as soon as it's built. It passes the linker `-platform_version macos <LSMinimumSystemVersion> <SDK version>`, so the binary records the SDK it was built with, as Xcode and SwiftPM's native build system (CI's) do: Swift Build, SwiftPM's default from 6.4, records the deployment target (14.0) instead, and AppKit decides some behaviour by that version, so a local build would differ from the release. (`--build-system native` did the same but is deprecated in SwiftPM 6.4.) 1.2.0, built with Xcode 16.4, recorded 15.5; 1.3.0 records 26.5 from CI. Each build passes `--disable-build-manifest-caching`: the native build system once failed a rebuild that reused another architecture's cached manifest. It joins the binaries with `lipo`, copies the result, `Info.plist` and `AppIcon.icns` into `build/Join.app`, and ad-hoc signs it with an explicit designated requirement, `identifier "com.poliuk.join"`. A plain ad-hoc signature's requirement is the hash of that exact binary, so TCC treated every rebuild as a new app and asked for calendar access again. Pinning the requirement to the bundle identifier keeps the grant across rebuilds. The trade-off: any locally built binary that claims that identifier inherits the grant, which is acceptable for a locally built app and goes away with a real signing identity. `make run` builds and opens it.
- **App icon:** an amber tile with a white countdown ring, three quarters left from twelve o'clock, around a dark camera. `scripts/make-icon.swift` draws it with Core Graphics on the macOS icon grid (a 1024-point canvas, an 824-point tile with 186-point corners, room for the shadow), renders every size of the iconset from the vectors rather than scaling one bitmap down (only the Retina files for 16 and 32 points: `iconutil` would store 1x files at those sizes in a legacy format that macOS 26 and later shrink onto a grey plate), and runs `iconutil` to write `Resources/AppIcon.icns`, plus `docs/AppIcon.png` for the README. `Info.plist` names it with `CFBundleIconFile`. The `.icns` is committed, so building needs neither the script nor `iconutil`; run `make icon` after changing the drawing. On macOS 26 and later the system masks the tile to its own icon shape and adds its glass edge; the icon fills the shape, so it isn't shrunk onto a grey plate. There are no dark or tinted variants: those need an Icon Composer `.icon` compiled by `actool`, which comes with Xcode. The app has no Dock icon, so the icon shows in places like Finder, Spotlight, Login Items, System Settings › Privacy & Security › Calendars and the system's calendar access alert.
- **CI:** GitHub Actions on `macos-26` with Xcode 26.6 (Swift 6.3, the macOS 26.5 SDK), named through `DEVELOPER_DIR` rather than taken as the image's default, which GitHub moves to newer Xcodes. `macos-15`'s Xcode 16.4 (Swift 6.1) can't read the 6.2 manifest, and the Xcode 27 image is still a preview. It runs on every push to main and every pull request: `swift build`, `swift test`, a universal `scripts/build-app.sh` like a release's, and the app, zipped with `ditto` because artifact uploads drop the executable bit, is kept as a workflow artifact. CI never publishes anything.
- **Releases:** pushing a tag `vMAJOR.MINOR.PATCH` runs `release.yml` on `macos-26`, with the same Xcode as CI. It checks that the tag is `vMAJOR.MINOR.PATCH` with no leading zeros (`AppVersion`'s rule, so installed copies can offer it), matches `CFBundleShortVersionString` and is on main, runs `swift test`, builds a universal app (`ARCHS="arm64 x86_64"`), zips it with `ditto -c -k --keepParent` (which keeps the signature valid), and creates the GitHub Release with `gh release create --verify-tag --generate-notes`, attaching `Join.zip`. GitHub's generated notes only list merged pull requests, so the workflow puts the commit subjects since the previous tag above them (without the "Release x.y.z" commits). The asset keeps that name in every release, so `releases/latest/download/Join.zip` always gets the newest build. The in-app update check (§14) relies on the same things: the `vX.Y.Z` tag, an asset named `Join.zip`, and the SHA-256 digest GitHub records for each uploaded asset. `scripts/release.sh` (`make release VERSION=x.y.z`) makes the tag: it requires a clean, up-to-date main and a version of three numbers without leading zeros, newer than the last tag, writes the version into both `CFBundleShortVersionString` and `CFBundleVersion`, commits "Release x.y.z" if that changed anything, makes an annotated tag, and pushes main and the tag atomically after asking. The branch model and recovery steps are in [RELEASING.md](RELEASING.md).
- **Distribution:** ad-hoc signed, not notarized, by decision. Gatekeeper blocks the first launch of each version downloaded in a browser until the user clicks Open Anyway in System Settings › Privacy & Security (on macOS 14, right-click › Open also works). A locally built copy isn't quarantined and opens directly, and neither is a version the app installs itself (§14), so Open Anyway is only needed for a copy downloaded by hand. TCC keeps the calendar grant across versions because every build, local or CI, has the same designated requirement. Notarization (Developer ID + `notarytool` before the zip) can be added to `release.yml` later without touching the app. Notifications (§5) need no entitlement, provisioning profile or `Info.plist` key, so the ad-hoc-signed app can ask for them, and macOS keeps their permission by bundle id; that a downloaded copy gets the prompt and keeps its grant across an update is still to be confirmed on a real build (§12). Ad-hoc signing does rule out restricted entitlements, such as the one Time Sensitive notifications need.
- **Sandbox:** off. Sandboxing requires a real signing identity to be meaningful; nothing in the app needs it. The updater (§14) also relies on it being off: it replaces the app's own bundle and can write to ~/Downloads.
- **Updates:** from 1.1.0, Join! checks GitHub once a day and, when the user clicks Install, installs the new release itself, without Sparkle (§14); from 1.3.0, Install only downloads and verifies it, and Install and Relaunch puts it in place. Copies of 1.0.0 have no updater and must be updated by hand once.

## 14. Updates

From 1.1.0, Join! looks for a newer release once a day and can install it itself. The user chose this on 2026-10-07: a daily check against GitHub, on by default with a switch in Settings › General › Updates, and an **Install** button that downloads the new version inside the app, so it isn't quarantined and needs no Open Anyway. 1.0.0 has no updater; copies of it are updated by hand once. From 1.3.0 (2026-10-15), Install only downloads and verifies the new version; Join! then says it's ready and keeps running until the user clicks **Install and Relaunch** (Ready, below). Copies on 1.1.x and 1.2.x install with their own flow, which replaces the app and relaunches as soon as the download is verified, so the update to 1.3.0 still relaunches at once; the new flow applies to updates from 1.3.0 on.

**Check.** `UpdateChecker` (`@Observable`, on the main actor like the rest of the app, owned by `AppModel`) asks a `ReleaseFeed` for the latest release. `GitHubReleaseFeed` sends one unauthenticated GET to `https://api.github.com/repos/Poliuk/join/releases/latest` with `Accept: application/vnd.github+json`, `X-GitHub-Api-Version: 2022-11-28`, `User-Agent: Join/<version>` and `Accept-Language: en`, on an ephemeral `URLSession` (no cookies, no cache) with a 20 s timeout. A 200 is decoded with `UpdateCheck.decodeRelease`; any other status is a failure. No token is shipped or used. The language header is set because `URLSession` would otherwise send the user's own languages and region (`en-GB,en;q=0.9`, say); the app is English only. So apart from the version in the User-Agent the request carries nothing about the user, but GitHub sees the Mac's IP address. The download (Install, step 2) sends the same User-Agent and `Accept-Language`.

`UpdateCheck.update(current:release:)` (JoinCore) turns the release into an `AvailableUpdate`, or nil when the release:

- isn't newer than the running app's `CFBundleShortVersionString`,
- is a draft or a prerelease,
- has a tag that isn't exactly `vX.Y.Z` (`AppVersion`: three numbers, no leading zeros, no suffix),
- has no `Join.zip` asset, or one that is empty or larger than 100 MB.

The update's page and download URLs are built from the validated tag (`https://github.com/Poliuk/join/releases/download/vX.Y.Z/Join.zip`); no URL from the response is ever followed. The asset's `digest` (`sha256:<hex>`) gives the expected SHA-256 (`AvailableUpdate.Digest.sha256`). Without one (`.missing`) the install skips the checksum, and so it does with one that can't be read (`.unreadable`, kept as GitHub sent it), which the installer logs; the signature is checked either way. A build whose version doesn't parse (`currentVersion` nil) never checks.

**Schedule.** `AppModel` calls `UpdateChecker.start(now:)` from its own `start()`, and `tick(now:)` from its 30-second clock and on wake (`NSWorkspace.didWakeNotification`). `UpdateCheck.isDue` decides: the switch is on; there has been no successful check yet, or the last one (`Preferences.lastUpdateCheck`) is at least 24 hours old, or in the future because the clock moved back; and no check has failed in the last hour. A success stores its time and the version it offered (`Preferences.offeredUpdateVersion`, nil when it found none). What a successful check does with what it found, to the status, the offer, the install and a stored release this Mac can't run, is decided by `UpdateCheckOutcome` (JoinCore), which `UpdateChecker` applies. A failure is kept in memory only, so a relaunch may try again sooner. **Check Now** checks whatever the switch says. One check runs at a time, and nothing installs while one runs: `installUpdate()` and `installAndRelaunch()` refuse, and Install and Install and Relaunch are disabled in the panel and in Settings. No check starts while Join! downloads, verifies or installs (`UpdateInstallState.isInProgress`); one that was already running when Install was clicked leaves the offer as it is.

The offer itself isn't kept across launches, only its version. At launch (`start(now:)`), with the switch on and `offeredUpdateVersion` newer than the running version (`UpdateCheck.rechecksAtLaunch`), `UpdateChecker` checks at once, due or not, and shows no offer until that check succeeds; if it fails (Join! opened at login before the network was up, say), it's retried an hour later like any failed check, not at the next daily one. Otherwise it ticks as usual. So an update found yesterday is offered again after a relaunch, but only if it's still the latest release. Together this makes about one request a day per Mac: one an hour while checks keep failing, plus one at a launch after a failure or while an update is on offer. Fixture runs keep `lastUpdateCheck`, `offeredUpdateVersion` and `unsupportedUpdate` in memory unless `JOIN_FIXTURE_UPDATE=live` (§12).

**Failures are quiet.** Being offline, a 403 or 429 (GitHub allows 60 unauthenticated requests an hour per IP address), a 5xx or JSON that doesn't decode all end in `UpdateStatus.failed`: Settings says "Couldn't check for updates", the panel shows nothing, and a failed automatic check never shows an alert.

**Install.** Installing takes two clicks, and `UpdateInstaller` (behind the `UpdateInstalling` protocol) does the work in two steps, both `@concurrent`, so their file and signature work runs off the main actor ([Concurrency](#concurrency)). **Install** runs `prepare()`, steps 1 to 5 below, which downloads and verifies the new copy and leaves it in the working folder; nothing is replaced and nothing quits. **Install and Relaunch** runs `install()`, steps 6 and 7, which verifies that copy again, puts it in place and relaunches, and returns `.relaunching` or `.revealed(URL)`. Either step can fail with an `UpdateFailure` (JoinCore: `download`, `tooLarge`, `checksum`, `unzip`, `notJoin`, `wrongArchitecture`, `unsupportedSystem(minimum)`, `signature`, `save`, `relaunch`). `UpdateChecker.install` follows it all as an `UpdateInstallState` for the update bar (§7) and Settings (§8):

| State | When | Bar | Button |
|---|---|---|---|
| `idle` | an update is on offer | "Join! 1.1.0 is available" | **Install** (disabled while a check runs; in a fixture run without `ready` or `live`, with "Not available in fixture mode.") |
| `downloading(fraction)` | after Install | "Downloading Join! 1.1.0… 45%" | none |
| `verifying` | the download is complete: steps 3 to 5 | "Verifying Join! 1.1.0…" | none |
| `ready` | verified; lasts until the user clicks, the offer changes or Join! quits | "Install 1.1.0" | **Install and Relaunch** (disabled while a check runs) |
| `installing` | after Install and Relaunch: steps 6 and 7 | "Installing Join! 1.1.0…" | none; Join! then quits and the new version opens |
| `revealed(URL)` | Install and Relaunch couldn't replace the running copy | "Quit Join!, then move Join! 1.1.0 to Applications" | **Show in Finder** |
| `failed(UpdateFailure)` | either step failed | "Couldn't install Join! 1.1.0" | **Download Page**; the tooltip and Settings say why |

`UpdateCopy.failureReason` says why in words ("The download didn't finish.", "This version needs macOS 15.0 or later.", …). The steps:

1. When Install is clicked, make a working folder, `Update-<process id>-<UUID>` in `~/Library/Application Support/com.poliuk.join/Updates.noindex/` (`UpdateInstaller.updatesFolder`), when that's on the app's volume, so the swap in step 6 is a rename, or when the app can't be swapped anyway (translocated, say: step 7 reveals the copy). Not in the user's temporary folder, where a ready copy may wait for days: macOS deletes the files there that are more than three days old, and an unzipped copy's files carry the release's dates from the start, since ditto keeps the archive's. `.noindex` keeps Spotlight from indexing the waiting copy as a second Join!. For an app on another volume, the working folder is an item-replacement directory on that volume (`FileManager.url(for: .itemReplacementDirectory, in: .userDomainMask, appropriateFor: Bundle.main.bundleURL, create: true)`), or a temporary directory if that fails. It's removed when a step fails, when step 6 or 7 ends, and when the download is discarded (Ready, below); a ready copy is the only thing it keeps between the two clicks.
2. Download `Join.zip` from the URL built from the tag with a `URLSession` data task whose delegate writes the bytes straight into `Join.zip` in the working folder, reporting progress. Only a 200 (after redirects) is accepted. A download that announces more than 100 MB is refused before its first byte, and one that grows past 100 MB is cancelled as soon as it does (`tooLarge`). Nothing goes through `URLSession`'s own temporary files, so a failed or cancelled download leaves nothing behind once the working folder is removed. The session is invalidated afterwards.
3. Check its SHA-256 (CryptoKit) against the digest, when the release has one.
4. Unzip it with `/usr/bin/ditto -x -k`, then delete the zip.
5. Verify the unzipped `Join.app`: its bundle identifier is the running app's (else `notJoin`), its `CFBundleShortVersionString` is the expected version (`notJoin`), its `LSMinimumSystemVersion` isn't above the running macOS (`unsupportedSystem`; `UpdateCheck.system(_:isAtLeast:)`, which lets a value it can't read through), its executable has a slice for this Mac's processor, arm64 on Apple silicon and x86_64 on Intel, as `Bundle.executableArchitectures` lists them (`wrongArchitecture`; checked after the macOS version, so a release for newer Macs ends in the lasting unsupported state below rather than a failure offered again every day), and its code signature is valid and satisfies `identifier "com.poliuk.join"` (`SecStaticCodeCreateWithPath`, `SecRequirementCreateWithString`, `SecStaticCodeCheckValidity` with strict validation, all architectures and nested code; else `signature`). The copy is now `ready`, and waits for Install and Relaunch.
6. On Install and Relaunch: if the ready copy is gone, or has lost its Info.plist or the executable it names (removed behind Join!'s back, say), the bar goes back to **Install**, which downloads it again. Otherwise verify it again as in step 5, since it may have waited for days in a folder this user can write to. A copy that no longer passes was damaged while it waited; nothing has been replaced yet, so it's removed and the bar goes back to **Install** too (`ReadyCopyDamaged`), rather than failing. Then replace the running app's bundle with `FileManager.replaceItemAt`, which swaps it atomically, and relaunch. `replaceItemAt` can throw after the swap, when it can't delete the old copy (a locked file inside it, say). So after an error Join! verifies what's at its own path: if it passes step 5 as the new version, the update is in place, and Join! removes what it can of the old copy and relaunches. Otherwise it goes on to step 7, after verifying again what it's about to reveal; if that fails, the install fails with `save`, so an unverified bundle is never revealed.
7. If the bundle's folder isn't writable, the app is running translocated, or the replace fails: move the verified app to `~/Downloads/Join <version>/Join.app` (a unique folder name if that one is taken) and reveal it in Finder. The bar says "Quit Join!, then move Join! 1.1.0 to Applications", with **Show in Finder**; if the copy isn't there any more (the user already moved it), Show in Finder puts the bar back to Install. Fixture runs reveal into `$TMPDIR/JoinUpdate/` instead and never touch ~/Downloads.

Any other error ends in `failed`, and the bar offers **Download Page**, except `unsupportedSystem` (below). The log (category `updates`) has the cause the bar's reason leaves out: the file error behind `save` or a checksum that couldn't be read, ditto's exit status, both digests when they differ. The zip comes in through `URLSession`, not a browser, so it carries no quarantine attribute and the new version opens without Open Anyway. The calendar permission carries over, since every build has the same designated requirement (§13).

**A release this Mac can't run.** GitHub's API doesn't say which macOS a release needs, so one that drops this Mac's macOS is offered like any other. When step 5 finds its `LSMinimumSystemVersion` above the running macOS, `UpdateChecker` stores the version and the minimum in `Preferences.unsupportedUpdate`, clears the offer, so the update bar goes away, and sets `UpdateStatus.unsupported`: Settings reads "Join! 2.0.0 needs macOS 15.0 or later", with no Install. That survives a relaunch. A later check that finds the same release keeps it that way and doesn't offer it; a newer release clears the stored value and is offered as usual, and so does the same release once the Mac runs a macOS that's new enough (`UnsupportedUpdate.stillUnsupported`). A release without a slice for this Mac's processor (`wrongArchitecture`) is a broken build rather than one for newer Macs, so it fails like any other error.

**Ready.** Between the two clicks the new copy waits in the working folder, and the bar and Settings stay as they are until the user acts; there's no notification or alert. `UpdateChecker` keeps the `UpdateInstalling` from Install on, so it can always discard the download (`discardDownload()`, which removes the working folder):

- **Quitting without the click** installs nothing. `AppDelegate.applicationWillTerminate` discards the download, ready or still under way (Join! opts out of sudden termination, so this runs on Quit, logout and restart). The next launch offers the update again as usual (`offeredUpdateVersion` brings the recheck at launch), and Install downloads it again. A crash or a force quit skips that and leaves the working folder behind. Nothing reuses it, and the next launch removes it: `start(now:)` runs `UpdateInstaller.removeLeftovers()` off the main actor, which deletes every `Update-<process id>-…` folder in `Updates.noindex` whose process isn't running any more. A folder whose process is running is kept, since it may hold that copy's ready update (a fixture run next to the real app, say). Fixture runs other than `JOIN_FIXTURE_UPDATE=live` never install for real, and don't clean.
- **Checks go on while ready** (daily, at launch, Check Now; `ready` isn't `isInProgress`). One that finds the same update keeps the ready copy. One that finds a newer release, or none (the release was deleted), discards it: the bar offers the new release with Install, or goes away (`UpdateInstallState.afterCheck(offerChanged:)`). A failed check keeps it. Install and Relaunch is disabled while a check runs.
- **Install and Relaunch never runs alongside the discard**: while it's `installing`, `discardDownload()` does nothing, since removing the folder under the swap could put a partly deleted copy in place; the step removes the folder itself when it ends.
- Every check and safety property of the one-click flow is kept: nothing is ready that hasn't passed step 5, the copy is checked again just before the swap, the swap is atomic, what's at the app's path is verified after a swap that throws, and only a verified copy is revealed. A ready copy that's gone or damaged when the second click comes goes back to **Install** (step 6): nothing was replaced, and the new download is checked from the start. Any other failure at the second click shows like any other (`failed`, Download Page); the next check that finds the same update offers Install again.

**Relaunch.** Join! starts a small `/bin/sh` loop that checks with `kill -0` every 0.2 s whether this process is still running and, once it has exited, runs `/usr/bin/open -n` on the new bundle. Then it calls `NSApp.terminate(nil)`. `-n` opens a new instance even when another copy with the same bundle identifier is running, as on a developer's Mac. A fixture run passes `--env JOIN_FIXTURE=<scenario>` (and `JOIN_FIXTURE_UPDATE`, if set) to `open`, so the relaunched copy is a fixture too. With `JOIN_FIXTURE_UPDATE=ready`, `FixtureUpdateInstaller` stands in for both steps (§12): a pretend download, then Install and Relaunch runs the same helper on the running bundle, replacing nothing.

**Trust model and its limits.**

- The trust anchor is HTTPS plus the GitHub account and its release workflow. Whoever can publish a release on Poliuk/join (the account, or a change to `release.yml` that reaches a tag on main) can put an update in front of every copy with the check on within a day, and two clicks, Install then Install and Relaunch, run it.
- The digest comes from the same API response as the release. It catches a download that was damaged or tampered with on the way, not a release that was bad when it was published.
- The signature check pins only the designated requirement `identifier "com.poliuk.join"`, the one every build is signed with (§13). An ad-hoc signature has no certificate behind it, so anyone can sign a bundle that satisfies it: the check refuses a damaged bundle or a different app, not a forged Join!. A Developer ID requirement (with a team identifier) would close that gap; it comes with notarization.
- Only newer versions are offered, so moving `latest` back to an older release never downgrades anyone. A bad release is fixed by the next patch ([RELEASING.md](RELEASING.md)). Deleting it stops new installs at once, since the download URL then fails; a copy already downloaded and ready still installs if Install and Relaunch is clicked before the next check, which finds the release gone and discards it. Marking it a pre-release only stops new offers, and copies that already found it keep offering it until their next check.
- Replacing a copy in /Applications hasn't been tested under macOS's App Management protection (System Settings › Privacy & Security › App Management). If macOS refuses the replace, the install falls back to revealing the new copy (step 7).

**Why not Sparkle.** Sparkle 2 is the usual updater for apps outside the App Store, and the earlier plan was to add it if updates were wanted. But it's a third-party framework (the app has none, §1), and it needs an appcast to publish and an EdDSA key to sign every release with, kept in the release workflow's secrets. GitHub's releases API already says which release is the latest and records a SHA-256 digest for each asset, so the updater is one request plus Foundation, CryptoKit and Security. What that gives up is Sparkle's own signature: a key kept outside GitHub would stop an update published from a compromised GitHub account.

## 15. Risks and mitigations

| Risk | Impact | Mitigation |
|---|---|---|
| Google → macOS Calendar sync lag (up to the user's refresh interval) | A meeting created 10 min before start may not alert | Document the refresh-interval setting; safety-net refetch; Refresh Calendars button; direct Google API as P2 if it bites. |
| `MenuBarExtra(.window)` quirks (can't dismiss programmatically, grows but never shrinks) | Panel stuck at its largest size | **Happened.** Replaced by `NSStatusItem` + `NSPopover`, and in the redesign by a borderless panel window sized from SwiftUI's measured height (§7). |
| Sizing AppKit windows from SwiftUI's measured heights | Layout loops, or a panel or Settings window stuck at the wrong size | Heights travel through preferences; the panel ignores changes under half a point; the panel and the Settings window resize on the next run-loop turn, never inside a layout pass; frames are only set when they differ. |
| macOS 14+ cooperative activation: a background app can no longer make itself active | Alert visible but Esc goes to the app the user was in; Settings opening behind other windows | **Happened**, twice. The alert is a non-activating panel that takes keyboard focus without activating the app (§6). The menu bar panel works the same way. Settings, an ordinary window that needs Join! active, opened behind the app in use now and then until 1.3.0: it's now put in front with `orderFrontRegardless` before activation is asked for, on the next turn, with the window on screen (§8). |
| One-shot timers unreliable across sleep / App Nap | Missed alert | Heartbeat + overdue-fires-now rule + disabling App Nap near fire time. This is the most important correctness property; it gets the most tests. |
| Custom alert colors that are hard to read | Alert misread or ignored | Automatic colors by default, named swatches that read on every preset, contrast warnings under 4.5:1 right under the row that causes them, Join fill never below 40 %, presets, Restore Defaults. |
| A pause left on by mistake | No alerts of either kind for the rest of the day, or at all | The menu bar item shows the crossed-out bell and the panel shows a paused bar with Resume; timed pauses end on their own. **Alert me** or **Notify me** set to **Never** is a setting, not a pause, so it shows no bell: it's a deliberate choice in Settings, and the menu bar and the panel keep working. |
| Script hooks accept notifications from any local process | Another program could pause alerts, dismiss an alert or open Settings | Only fixture runs register them, and they only do what a click could do. Nothing leaves the Mac, except an update check in a fixture run with `JOIN_FIXTURE_UPDATE=live`. They can be limited to debug builds if that ever matters. |
| No Apple Developer membership | Gatekeeper friction for users | Ship ad-hoc signed; document Open Anyway in System Settings › Privacy & Security (right-click › Open on macOS 14); updates installed from the app skip it (§14); notarize later. |
| A bad release goes out | Every copy with the update check on offers it within a day | Install refuses a damaged zip, a different app, the wrong version, or a build without this Mac's processor (§14). Delete the release: `latest` and `releases/latest/download/Join.zip` fall back to the previous one, an Install already on offer fails at the download, and a copy already downloaded and ready is discarded at the next check (it installs only if Install and Relaunch is clicked before then). Marking it a pre-release only stops new offers: copies that already found it keep offering it until their next check. Copies that installed it get the fix with the next patch ([RELEASING.md](RELEASING.md)). |
| The GitHub account or the release workflow is compromised | A forged update offered to every installed copy | Accepted for now: the identifier-only signature requirement can't tell a forged build apart (§14). A Developer ID requirement, or a signing key kept outside GitHub, would. |
| GitHub's API is down or rate-limits the check | No update offered | About one request a day per Mac; a failure only shows in Settings, and the next try waits an hour. |
| EventKit doesn't expose structured conference data | Join link missed for exotic providers | Regex table + generic `https://` fallback from location; easy community contributions. |
| Notifications from an ad-hoc-signed, non-notarized build | No prompt, nothing delivered, or the permission lost with an update | Local notifications need no entitlement, and macOS keeps the permission by bundle id (§13). To be confirmed on a real build before 1.3.0 ships (§12); the full-screen alert doesn't depend on it. |
| macOS holds notifications during a Focus and, by default, while the screen is shared | Someone with notifications only misses a meeting while presenting, the problem Join! exists to solve | No Time Sensitive without a restricted entitlement (§5), and Join! can detect neither. The Notification box's footnote says so; the full-screen alert ignores both and stays the default. Accepted with Direction A (2026-10-16). |
| Notification permission is asked only once | A user who declines, or misses the prompt in the corner, gets no notifications | Asked in context, when Notify me first gets a time or Test Notification is first clicked, never at launch. The status line explains, with Open System Settings; the `?id=` deep link is undocumented, so it falls back to the Notifications pane. |
| A calendar's own event alerts notify too | Two notifications for one meeting | Notify me is Never by default; the README says so neutrally. Join! can't tell. |
| `.screenSaver` window level fights with macOS lock screen / actual screen saver | Alert hidden behind lock screen | Acceptable: if the screen is locked the user isn't there. The alert remains until dismissed. |
